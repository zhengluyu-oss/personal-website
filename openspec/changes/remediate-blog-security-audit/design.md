## Goals / Non-Goals

**Goals:**

- 让每项确认风险都有可复现的本地失败用例、修复及回归验收；同时检查合法路径。
- 从入口、业务授权、异步消费者、输出渲染与构建发布几个边界共同约束敏感数据。
- 保留博客、个人经历、网站分享、文件上传及第三方登录业务能力。
- 明确前后端兼容、短期凭证失效、发布验证及生产操作授权条件。

**Non-Goals:**

- 不重新设计整个登录系统，不默认迁移全部 JWT 到 Cookie，不新增独立 IAM 服务。
- 不全盘重构内容数据库，不改写项目经历，不执行生产攻击或发送测试邮件给真实用户。
- 不自动删除历史日志、轮换云端密钥、调整安全组/OSS 策略或部署线上环境。
- 不以扫描告警总数宣称漏洞数量，不要求无依据地强制升级所有依赖到最新大版本。

## Decisions

### 1. 预览按内容类型选择安全输出

留言、评论及其收藏快照按纯文本显示；文章类 Markdown 复用已经建立的 HTML 净化边界，审计两个前端所有同类预览，保证最后进入 DOM 的结果已过滤事件、危险协议和活动内容。渲染历史数据时同样净化，不依赖一次性清库。收藏创建验证目标存在、类型受支持和当前用户可访问；后台读取缺失目标返回受控的不可用状态，不能空指针或转用其他记录。

不采用单纯在输入端删 `<script>` 的方案：事件属性、SVG、协议与历史内容仍可绕过。保留合法标题、表格、代码块和链接；新增净化依赖前先复用仓库现有能力。

### 2. 日志在入队前最小化，消费端防御性复核

新增或复用单一结构化审计投影器：认证/验证码/令牌相关操作仅记录操作名、内部主体 ID、结果码、耗时、请求关联 ID 等允许字段，不记录完整 DTO、响应和任意异常消息。其他业务采用明确字段策略，递归遮蔽嵌套对象、列表、Map 的密码、验证码、Authorization、Cookie、token、secret 等字段并限制深度和长度；拒绝对未知对象调用任意 `toString()`。

正常和异常分支在序列化及入队前使用同一策略；日志消费者对旧消息执行复核，无法安全解释的载荷丢弃敏感部分而保留事件元信息。保留业务可追踪性，不用“完全关闭日志”掩盖问题。失败只记录安全错误标识及受控内部诊断，不将敏感输入拼接进异常。

历史处理独立于业务发布：只读统计受影响时间段、日志类型和数量，不输出值；输出授权清单和受限备份方案，再由操作者批准脱敏/清理。确认泄露后评估对应凭据轮换，不能把删除日志当成泄露补救的全部。

### 3. 邮箱变更使用用途绑定的再次认证

统一邮箱变更服务，由持久化账号类型和现有绑定状态选路径：密码账号必须验证当前密码；管理员额外验证当前已绑定邮箱的二次因素。第三方账号首次绑定要求近期再次完成相同 provider 和 provider subject 的认证；已有邮箱的第三方账号换绑还需原邮箱证明。新邮箱验证码只能证明新地址控制权，不能单独授权换绑。旧邮箱不可用时拒绝自动换绑并提供人工恢复说明，本变更不引入弱恢复入口。

再次认证证明使用安全随机标识，Redis 保存摘要及账号、用途、目标邮箱、凭据版本、到期时间；有效期 5 分钟，最多 5 次验证失败，成功原子消费。目标邮箱码与证明绑定并受既有限流保护，不允许登录验证码与换绑验证码互换。每次证明只允许发起一次数据库更新；失败后重新验证，不恢复可重放证明。数据库更新再次校验账号原状态并处理邮箱唯一性冲突。

2026-10-02 经用户确认，增加 `sys_user.email` 唯一索引迁移，不再假设应用层先查后写可以保证唯一性。保持现有列排序规则及跨账号类型、停用/软删除账号的占用语义；NULL 仍允许表示未绑定。迁移只增加索引，不改邮箱值、不合并或删除账号。先只读统计重复组及空白异常数量，发现冲突即停止；DDL 本身仍检查并发写入冲突。注册、OAuth 建号和邮箱修改均需处理数据库唯一冲突，不自动把第三方身份关联到已有邮箱账号。迁移首次/重复执行、冲突保持原记录及并发写入在隔离 MySQL 中验证。生产执行仍需单独授权、备份和维护窗口。

扩展现有 credentialProof，绑定每账号不可复用的随机认证版本，而非仅对邮箱重新计算摘要。认证版本置于独立 Redis 命名空间，邮箱变更时先轮换版本并撤销旧挑战，再执行条件更新；数据库更新失败也保持旧会话失效这一安全结果。验证时版本缺失或 Redis 不可用则拒绝已有 token；仅完整登录可原子初始化新版本，版本不按邮箱值恢复，防止邮箱改回原值后旧 token 复活。清除账号认证缓存，认证读取不得使用旧版本缓存。避免新建全局会话数据库。上线引入版本会使旧会话需要重新登录，应作为发布影响说明；后续普通登录仍为既定 24 小时，不以滑动无限续期代替有效期。

### 4. OAuth 从发起阶段绑定浏览器

服务端登录发起接口生成随机 state 与每次尝试的浏览器秘密，在 Redis 存储摘要、provider、用途（登录/再次认证）及回跳白名单；浏览器秘密通过 HttpOnly、Secure、SameSite=Lax 的短期 host-only Cookie 保存，作用域仅限认证路径。开发环境只能在明确的 localhost 配置中放宽 Secure。

provider 回调校验 state/provider 后产生两分钟单次兑换码，但码仍绑定浏览器秘密；兑换时校验关联后原子消费。错误浏览器的请求不能消费他人有效码；重放、过期或 Redis 故障均拒绝发 token。保留 GitHub/Gitee 支持和管理员双因素要求。回跳地址不接收任意外部 URL。

前端仅为本浏览器发起的尝试兑换，尽早清理 URL；已有有效会话时不自动覆盖 token，要求明确退出或确认切换后重新发起。无需前端持有 provider token。与只增加随机兑换码相比，这一设计解决的是“是谁发起登录”，而非仅防猜测。覆盖并行标签页；按 state 区分有限数量尝试，不能让一个标签页消耗另一个尝试。

### 5. 对象删除由业务归属决定，不由 URL 决定

保留上传响应中的 HTTPS URL 字符串及 multipart 契约。服务器在成功上传文章封面后登记 Redis 临时上传凭据（owner、规范 key、用途、状态），有效期 24 小时。封面删除改为非 GET 的同路径操作，可接受原 URL 作为定位值，但授权必须来自服务器凭据与数据库引用，不能仅检查目录前缀。

仅允许当前发布者删除自己未被任何文章引用的临时封面。编辑已发布封面时先保存新引用，旧对象本次不通过通用临时删除接口清除，避免删除共享图片；暂不做自动孤儿清理。过期或无归属记录的历史图片默认拒绝临时删除，必要时重新上传，不为兼容重新放开任意 key。保存文章与临时删除必须使用同一对象状态锁/原子状态转换，数据库引用检查在该保护下执行，防止“检查未引用后被引用”的竞态；共享引用也走同一校验。

URL 解析只接受配置的精确 HTTPS 存储源和允许目录，拒绝其他 host、userinfo、混淆编码、路径穿越及任意原始 key。管理员头像、横幅等内部替换逻辑使用各自权限和数据库记录派生 key，不复用对客户端无边界的删除入口。删除结果必须反映真实结果，OSS 失败不能报成功。

新增表虽然可实现持久归属，但本次仅需约束临时清理，选择 Redis 以避免数据库迁移；持久媒体资产库不属于本次范围。

### 6. 上传校验实际内容并限制解析成本

上传目录、后缀和尺寸限制保留，增加扩展名、服务端探测 MIME、签名/解码结果的一致性检查。为图片设置像素/解码预算，拒绝伪装 HTML/SVG 等活动内容；已有视频用途使用独立媒体类型及签名验证，不误套图片解码器。OSS Content-Type 从服务端验证结果生成，不能信任 multipart 声明。校验失败之前不得执行替换对象的旧文件删除。

### 7. 邮件审批不再是匿名 GET 状态变更

使用至少 256 位随机审批 token，Redis 仅存摘要、linkId、用途、过期时间和状态，有效期 24 小时。GET 只展示确认流程，不修改友链、不消费 token；真正审批使用 POST，要求已登录管理员和 `blog:link:isCheck` 权限，并校验 token 对应记录仍待审核。无权限请求不消耗凭证；成功请求原子认领并以待审核状态为条件更新数据库，失败需重新签发，不允许重复副作用。

邮件链接避免在日志中记录凭证，落地页不引入不必要的第三方资源，设置不发送来源地址的策略并尽早清理地址中的 token。使用新命名空间隔离并拒绝旧时间戳凭证；保留后台列表直接审批能力。单纯把时间戳换 UUID 仍无法防止邮件安全扫描器触发自动审批，因此必须同时调整交互和权限。

### 8. 评论与异步通知共享可见性判定

建立类型到目标查询的明确映射，公共读取先验证父目标存在、公开且满足对应审核规则；回复和收藏提交同样验证目标。parentId/replyId 必须属于同一 type/typeId 的有效、可见线程，replyUserId 从实际回复记录推导，客户端不具备指定任意收件人的能力；冲突字段拒绝而不是静默跨目标拼接。

未审核新评论不立即对其他用户发出包含正文的通知。审核通过且事务提交后产生仅含必要 ID 的通知事件；消费时重新读取目标、原回复和新评论的可见性并检查收件人通知偏好、去重状态。期间删除、转私密或撤回审核均取消通知。站内通知列表及其查询也必须避免暴露私密标题和未审核内容。管理员审核视图保持独立权限，不可被当成公共可见性证明。

### 9. 发布包不携带本地秘密，升级以可达性分组

保留本地 gitignored 配置供开发使用，但 Maven 发布资源仅纳入明确安全的配置/模板，不打入 dev 或私有 profile 文件。生产脚本显式选择 prod；外置配置/环境变量提供必需秘密，缺失启动失败，不能落回开发账号。对最终 JAR/前端 dist 做路径和敏感模式检查，仅输出位置与规则、不输出值；starter-test 恢复 test scope。

建立两个前端生产锁文件和后端最终 JAR 的清单；按运行时、构建期、开发期及实际调用路径分类公告。既有扫描报告（前台 23、后台 93 项）只是基线，不是已证实漏洞数。逐组升级 Spring Boot 兼容 BOM、Tomcat/Spring Security、Markdown/图表/HTTP 等依赖，核对 Java 17、MyBatis 与 Vue 兼容性；不执行强制全量自动修复。确认可达的高危/严重问题必须修复；不可达或待上游修复项记录证据、补偿措施、负责人和复查日期，经确认接受，不能静默忽略。

实施时按当前官方公告选择受支持修复版，不把审查时的最低修复版本当长期目标。参考 Apache Tomcat 官方安全公告及 md-editor-v3 官方仓库安全公告；若报告需共享，移除内部路径、凭据与未公开业务内容。

2026-10-03 用户已批准两个前端统一使用 pnpm，以及移除后台 Mist 构建命令包装器、直接使用受维护的 Vite。保留 Vue、Ant Design Vue、已有路由、API、数据库和静态部署方式；当前明确关闭的 Nitro 不作为新功能迁移。保持既有浏览器构建目标、子路径、别名、自动导入和公开配置生成，适配必要插件并补充本地构建/预览/代理验证。不因该批准执行生产部署。

### 10. API 和浏览器边界显式配置

依赖决策补充（2026-10-03）：用户已确认升级 Spring Boot 4.x 及必要兼容改造，保留 Java 17。先按官方迁移建议检查 3.5 阶段，再使用受维护的 4.0 系列，统一 MyBatis-Plus 启动组件，验证 Spring Security、Jackson、Redis 编码、文档入口与打包配置；不以编译代替业务验收，不执行生产部署。

先产出路由清单，逐项区分公开读取、认证、管理权限和外部回调，默认拒绝未分类路由；保留现有 method-level 权限作为第二层。登录、验证码、公开文章/经历/分享及必需回调显式放行，而非路径模糊匹配。普通用户不能通过前端身份头获得后台权限。

CORS 由配置列出精确 scheme/host/port，不回显任意 Origin；拒绝不允许的预检，正确设置 Vary: Origin、必要方法与头，同源/无 Origin 的正常服务调用不受误伤。CORS 不是认证替代品。

Nginx 增加 nosniff、Referrer-Policy、frame 限制，页面 CSP 先 Report-Only、验证后强制，限制 script/object/base/frame 等关键来源，资源域名依据实际前端使用核对。避免 `unsafe-inline` 脚本掩盖 XSS，必要内联脚本用 hash/nonce；样式与 Markdown 渲染按最小兼容策略。HSTS 从短 max-age 验证，再提升；未验证全部子域前不启用 includeSubDomains/preload。Report-Only 不是最终完成状态。

## Risks / Trade-offs

- [发布后旧会话失效] → 提前告知需要重新登录；保持新的 24 小时有效期和双因素认证。
- [封面临时凭据丢失或过期] → 拒绝删除且保留对象，不以数据损坏换取清理便利；提示重新上传。
- [Redis 与数据库不能跨系统事务] → 凭证先原子认领、数据库条件写入、失败重新验证；通知使用提交后事件和幂等消费，优先拒绝而非重复执行。
- [默认拒绝漏列公开页面] → 从路由清单建立匿名/用户/管理员矩阵，覆盖两个前端全部业务入口后再部署。
- [CSP、依赖升级损坏编辑器或 OAuth] → 分批实现和测试，真实配置下预发布验证；不直接在生产调试。
- [本地配置虽未进 Git 但已随包传播] → 包内删除不等于密钥安全；核实传播范围，再授权轮换。
- [历史数据含活动载荷或敏感字段] → 输出时保护立即生效；清理单独备份、确认、执行，不默认删除用户内容。

## Migration Plan

1. 建立路由、敏感日志、资源使用和依赖基线；所有截图/测试使用本地虚构数据。编辑符号前执行 GitNexus impact，记录 HIGH/CRITICAL，UNKNOWN 补充源码核查。
2. 优先修复渲染、日志及换绑，再修复对象/评论/邮件/OAuth，最后收紧接口、包和依赖。每组同时提交自动化回归用例，但本变更不自动执行 Git 提交。
3. 生成可重复构建及新旧接口差异清单，校验 Redis 编码不影响既有双因素 key；邮箱唯一索引按已批准的加法迁移执行，其他业务表不重构。先完成只读预检，存在重复数据则阻止发布并请求所有者处理，不自动清理。
4. 经单独部署授权后，备份当前发布包和配置到受限位置；协调前后端发布、加载新配置，旧凭证失败关闭，验证匿名浏览、登录/双因素、上传、审批和通知。
5. CSP 先观察再强制，HSTS 渐进启用；生产验证不发送攻击载荷、不操作真实无关对象。
6. 若需要回退，优先保留安全后端并回退兼容前端；必要时临时关闭换绑、旧删除及邮件审批入口。不得恢复存在已确认绕过的旧接口来保持可用性。已轮换的密钥不回滚为旧密钥，含秘密的旧包不能作为默认回退目标。
7. 将历史日志治理、实际密钥轮换与发布验证作为独立操作清单；无授权时标明未执行及剩余风险，不声称线上已修复。
