## Context

管理员二次验证挑战由 `AdminLoginChallengeServiceImpl` 写入 Redis，并通过 Lua 脚本原子比较验证码摘要、累加失败次数和消费挑战。当前服务注入的是配置了 `FastJsonRedisSerializer<Object>` 的通用 `RedisTemplate`：Hash 值和 `execute` 的脚本参数会以 JSON 字符串形式写入。Lua 中直接调用 `tonumber` 时会收到带 JSON 引号的字节内容，因而 `attempts` 与最大尝试次数均可能成为 `nil`；脚本随后执行大小比较，产生 `attempt to compare two nil values`，Spring 最终返回 HTTP 500。

现有挑战仅存活五分钟，不涉及数据库。邮件投递、管理员邮箱和第一因素密码均已在生产环境验证正常。

## Goals / Non-Goals

**Goals:**

- 让挑战字段与 Lua 参数使用确定的纯字符串序列化，恢复管理员验证码校验。
- 保持验证码校验、失败次数累加和成功消费的原子性。
- 将错误验证码、过期挑战和耗尽挑战作为受控认证失败处理，不再产生 HTTP 500。
- 让管理后台在验证码阶段展示对应提示，而不是用户名或密码错误。
- 用自动化测试复现并防止 Redis 序列化回归。

**Non-Goals:**

- 不修改管理员密码、管理员邮箱或数据库数据。
- 不改变验证码有效期、最大尝试次数、重发冷却、邮件模板或 JWT 签发规则。
- 不引入新的缓存、邮件或认证框架。
- 不处理与本次登录请求无关的历史邮件投递失败记录。

## Decisions

### 为二次验证挑战使用字符串 Redis 操作

管理员挑战的键、Hash 字段、Hash 值和 Lua 参数本质上全部是字符串，因此该服务改用 Spring 已有的字符串 Redis 模板（或等价的显式 `StringRedisSerializer` 执行路径）。挑战写入使用字符串 Map，Lua 参数也由字符串序列化器传入，使 `HGET attempts` 与最大次数参数可以稳定被 `tonumber` 解析。

选择该方案而不是在 Lua 中剥除 JSON 引号，因为后者把 Java 端序列化细节泄漏到脚本中，且无法稳健覆盖不同 JSON 值类型。也不修改全局 `RedisTemplate`，以免影响项目中其他现有缓存格式。

### 保留 Lua 原子消费语义并增加防御性类型处理

验证码摘要比较、失败次数递增、达到上限删除以及成功后删除仍在单个 Lua 脚本中完成。脚本对缺失或不可解析的计数字段采用安全失败，不允许绕过尝试上限，也不把脚本异常暴露为 500。

选择继续使用 Lua 而不是 Java 的“读取后写入”，因为后者在并发提交时会产生重复消费或丢失计数。

### 使用现有业务响应表示预期的验证码失败

控制器边界将验证码错误、挑战过期/不存在和尝试耗尽映射为现有验证码失败业务响应，响应内容不区分账户或挑战是否存在。意外的 Redis 连接故障仍作为真正的服务异常记录，避免把基础设施故障伪装成用户输入错误。

### 前端按登录阶段显示错误

首次账号密码提交与验证码提交维护独立的错误状态。验证码阶段收到业务失败时保留二次验证界面并清空验证码输入，显示“验证码无效或已过期，请重新获取”等可操作提示；只有第一阶段失败才显示账号或密码错误。错误通知不再拼接原始 `AxiosError` 对象。

## Risks / Trade-offs

- [部署瞬间仍存在旧序列化格式的挑战] → 旧挑战最长五分钟后自然过期；部署后要求管理员重新开始登录，不迁移短生命周期验证码数据。
- [修改全局 Redis 配置可能破坏其他缓存] → 仅在管理员挑战服务内使用字符串序列化，不改全局模板。
- [吞掉真正的 Redis 故障会降低可观测性] → 只转换可预期的挑战校验结果；连接或执行异常继续记录完整服务端日志并返回通用服务错误。
- [更明确的前端提示可能泄漏挑战状态] → 对错误、过期和耗尽统一使用相同提示，不暴露账户存在性或剩余次数。

## Migration Plan

1. 完成后端单元/集成测试和管理后台构建验证。
2. 备份当前后端 JAR 与管理后台静态资源，不修改数据库或 Redis 全局配置。
3. 部署后端和管理后台；现有未完成挑战直接放弃，由管理员重新发起登录。
4. 在生产环境验证：密码阶段创建挑战、邮件送达、正确验证码签发会话、错误验证码返回受控响应且无 500。
5. 若验证失败，恢复上一版 JAR 和管理后台资源；已有挑战继续依赖其 TTL 自动清理。
