## Context

用户已确认：只有日记使用 PostgreSQL，既有博客保留 MySQL；日记按篇记录，一篇可包含过去十几天的经历，同一天可写多篇并持续补写，每篇可选填内容起止日期；允许后续云端 AI 分析，但本阶段仅完成私密日记与可靠保存。现有前端为 Vue/Pinia/Element Plus，后端为 Spring Boot 4.0.8、Java 17、Spring Security 和 MyBatis Plus，已有安全 Markdown、前台会话、Redis/RabbitMQ 与内容日志脱敏能力。

源码核对发现：`MybatisPlusConfig` 全局扫描原有 Mapper 并固定 MYSQL 分页方言；`SecurityConfiguration` 对未显式纳入认证的路径使用 permitAll；`LogAspect` 会投递经过脱敏的请求和响应。因此日记必须独立绑定 PostgreSQL、显式加入认证边界，并验证日记正文不会进入现有日志/消息链路。不能仅依靠菜单隐藏。

工作区有已归档但未提交、未全部验收的旧修复。GitNexus 元数据对应 HEAD `3b065edc29c755701612dfac873df1b4f1925244`，MCP 搜索仍有旧缓存提示，CLI context 已核对相关符号；本次新增规划目录未被索引，File impact 为 UNKNOWN/not found，只确认其为 CLI 创建的文档范围，不作为未来代码修改的许可。实施前仍需更新并核查实际工作区图谱，逐符号 impact，保留无关改动。

## Goals / Non-Goals

**Goals:**
- 本人在博客前台按篇自由记录及补写，可选择内容覆盖日期，完成日历/列表查阅、时间与文字筛选、历史恢复、删除和个人导出。
- 有准确且可验证的保存确认；网络失败、重复请求、并发标签页和页面切换不静默丢失或覆盖记录。
- 日记、历史和变更凭据同库提交；原有 MySQL 连接、事务、分页和公开博客能力保持可用。
- 新增 PostgreSQL 可独立关闭、部署、备份与恢复，有真实数据库验证证据。

**Non-Goals:**
- RAG、pgvector、Embedding、大模型、日报/行为评分、目标跟踪、定时提醒和新消息队列。
- 日记公开、分享链接、普通注册用户写日记、后台管理员跨账号读取、附件/图片/音频上传、导入和永久销毁。
- 整站迁移 PostgreSQL、新增后端服务或 ORM 框架、重做认证/导航/现有部署流程。
- 浏览器离线持久化、跨设备实时协作、端到端加密、强制每日打卡或将多日内容自动拆篇。网络未确认且页面进程被终止的内容不能承诺已保存。

## Decisions

### 1. 本人入口与数据边界

新增 `/diary` 前台工作区，以 `entry=<UUID>` 选择日记；新建动作生成独立草稿ID，不用日期定位唯一日记。用户菜单仅在服务端资格确认后提供“我的日记”，页面资源懒加载。`/diary/auth/**` 全部 HTTP 方法显式要求现有前台身份，业务服务再验证当前有效用户 ID 等于外置配置 `diary.owner-user-id`。不默认使用 ADMIN 角色、用户名或猜测的账号编号；管理员端 token 不自动转换为前台会话。

认证后的 `GET /diary/auth/capabilities` 仅返回 `allowed`、`available` 等布尔状态，不泄漏配置的 owner ID、日记数量或连接信息。匿名 401；非站主对实际日记 API 一律 403，包含其他管理员；站主遇到不可用模块收到 503。客户端不能指定 owner，所有 DAO 条件从已验证身份派生。

日记不接入文章表、公共搜索、推荐、站点地图、模块公开数量或公共上传。私密接口统一 `Cache-Control: no-store`，页面禁索引，SEO 不填正文/标题。检索词用 POST JSON，避免出现在 URL 和访问日志中。日志仅记录账号编号、动作、日期、版本、请求关联 ID 与结果，排除标题、正文、快照、关键词、导出内容、凭据及含参数 SQL；核对成功、异常、代理访问和审计消息链路。

替代方案：复用私人文章会扩大既有公开链路的泄漏面；只用管理员角色无法表达“仅本人”；单纯前端隐藏不能限制直接请求。

### 2. 独立连接与事务，保护现有 MySQL

沿用现有后端，新增由当前 Boot BOM 管理版本的 PostgreSQL JDBC runtime 驱动。日记 DAO 使用独立 `NamedParameterJdbcTemplate`（或现有等价 JDBC 能力）及明确命名的 `diaryTransactionManager`，不进入原 MapperScan 或 MYSQL 分页插件，不引入动态路由数据源依赖。

增加自定义 DataSource 可能使 Boot 默认 MySQL 自动配置退让，不能仅添加一个 PG Bean 即认为完成。实现时显式确认并保护 MySQL 主 DataSource、主事务管理器与 MyBatis SqlSessionFactory 的绑定；所有日记事务以 qualifier 指向 PG。当前 Boot 版本的具体装配方式通过双库真实测试确定，不照搬其他大版本示例。MySQL 只提供现有登录和用户状态，不与 PG 做跨库写事务或外键。

默认 `diary.enabled=false`；关闭时不建立 PG 连接，现有生产配置不新增必填项。启用后检查 owner、URL、独立运行账号和密码；不完整配置只使日记不可用并拒绝所有数据访问，记录缺失配置键名，原生产秘密保护不放宽。连接池采用显式小上限（初始建议 max=3/minIdle=0）、连接与 SQL 超时；关闭启动时强制连接/自动建表，故障不拖垮公开博客启动与健康探针。日记连接不可用时返回受控 503，不回退 MySQL、内存或 Redis 假保存。

PostgreSQL 主版本与镜像摘要在实施时确认，优先复用可获得的受支持版本（现有本地已有 PG16 系列测试镜像），不用 latest；第一阶段无需 vector 扩展或 GPU。配置、运行角色、迁移角色及数据库数据目录独立于原 MySQL。

### 3. 数据模型与一次原子变更

使用独立 `diary` schema，至少三张表：

| 表 | 核心内容与约束 |
| --- | --- |
| `entry` | UUID主键、owner_id、可空covered_from/covered_to DATE、display_timezone、title、body、revision BIGINT、created_at/updated_at/deleted_at TIMESTAMPTZ；不设置日期或时间范围唯一约束 |
| `entry_revision` | 所属日记、owner_id、revision、标题/正文/内容起止日期完整快照、操作类型、保存时间、来源历史版本；`UNIQUE(entry_id,revision)` |
| `mutation` | owner_id、mutation_id UUID、entry_id、操作/请求摘要、结果版本及保存时间；`UNIQUE(owner_id,mutation_id)`，不重复记录正文到日志 |

一篇日记由稳定UUID标识，允许同一天或相同覆盖时间内有多篇，时间范围重叠不构成冲突。created_at 是首次提交时间，updated_at 是最近变更时间；内容覆盖范围是独立可选元数据，界面明确标为“记录的时间范围”。起止日期可同时留空；填写时两端均须是有效日期且起日不晚于止日，单日填写为同日起止。日期按DATE保存，不作UTC位移；创建/修改时间按Asia/Shanghai展示，跨午夜和修改覆盖范围均不改变日记ID、created_at或拆分文章。正文中仍可自由写小日期标题，不强制按天分段。

新建草稿在浏览器内生成UUID，未发生编辑不写数据库；首次提交才创建entry。将内容起止日期纳入版本快照、冲突判断和请求摘要，恢复旧版本时同时恢复这组元数据。向后续AI提供这些字段时必须区分“写下这篇的时间”和“经历所处时间”，不因为一篇覆盖十几天就声称其中每天都有完整记录。

写入统一接收稳定 `entryId`、`mutationId` 和 `expectedRevision`：首次POST创建以预期版本0提交，已存在entry通过PUT基于当前版本更新。每次修改在一个PG事务内认领幂等键、执行UUID唯一键/CAS条件写、写不可变历史快照和保存幂等结果；任一步失败整体回滚。相同owner+mutationId、相同完整请求摘要返回原结果；同ID不同内容拒绝409。幂等重放先于版本冲突判定，解决“已经提交但响应丢失”；创建重试沿用原entryId及mutationId，不能新建重复日记。两个不同草稿ID在同一天提交都可成功；只有同一entryId的首次创建或版本写入竞争才冲突。不同请求ID的相同内容/时间范围在版本吻合时可返回不变版本，不产生空历史。

保存成功响应包含entryId、mutationId、revision及数据库保存时间；Controller只在事务提交后返回成功。相同UUID竞争、过期expectedRevision、删除后旧请求重试均不得覆盖当前版本；冲突返回安全错误标识及站主可读取的最新版本编号，由独立读取取得当前内容，不将SQL或其他用户正文放入错误。

不通过 Redis 锁/缓存作为写入权威，不采用无条件 upsert/最后写入覆盖，不在此阶段增加 outbox 或 MQ。为后续 AI 保留稳定 entry ID、内容 revision 和时间，不预建向量、分析报告表。

### 4. 可实施的接口边界

所有路径均在 `/diary/auth` 下，示例协议如下，保持项目已有成功响应外壳，并对 401/403/409/503 设置真实 HTTP 状态，日记客户端只读自身端点处理。

| 方法与路径 | 行为 |
| --- | --- |
| `GET /capabilities` | 本人资格与模块可用状态，不访问或返回日记内容 |
| `POST /entries` | 以客户端草稿UUID、expectedRevision=0、mutationId及正文/可选时间范围创建一篇 |
| `GET /entries/{id}` | 读取本人active/deleted记录；不存在或不属于本人均不返回内容，读取不创建 |
| `PUT /entries/{id}` | 参数化保存title/body/coveredFrom/coveredTo、expectedRevision、mutationId；owner不可指定 |
| `POST /entries/search` | 时间筛选轴（created或covered）、范围、关键词及分页；只搜当前未删除版本 |
| `GET /calendar?month=YYYY-MM` | 按创建时间归属的本地日期返回篇数，选择日期查看该日多篇，不把一篇多日内容算多篇 |
| `GET /entries/{id}/history` | 对本人的一篇日记按版本倒序分页，包含可恢复的删除历史 |
| `POST /entries/{id}/restore` | 校验来源历史版本及当前expectedRevision，以新版本恢复内容和时间范围 |
| `DELETE /entries/{id}` | JSON带expectedRevision、mutationId，按ID写墓碑和历史，不接受GET删除 |
| `POST /export` | 指定时间筛选轴、范围及Markdown/JSON；导出已提交的当前未删除内容 |

删除保留原UUID墓碑；同一日期仍可另外新建其他ID的日记，但删除前的旧保存不能复活原ID。恢复必须显式按ID操作。确认弹窗写明“移入已删除记录，可从历史恢复”，不承诺永久销毁；界面支持明确查看已删除记录，默认列表和日历计数排除。

查询使用owner/updated_at/id、owner/created_at及按需的覆盖日期索引和绑定参数；默认列表按updated_at降序、id稳定消歧，日历只体现创建日期。筛选区明确区分“写作时间”和“记录的时间范围”：created轴把Asia/Shanghai日界转成TIMESTAMPTZ半开区间；covered轴使用闭区间相交条件 `covered_from <= filter_to AND covered_to >= filter_from`，不是创建日期也不是仅看起日。不填覆盖范围的日记仍在默认列表和写作日历中，主动选择covered筛选时不匹配，并明确提示这一规则。一篇跨日记在结果中只出现一次，不截断正文或复制为每日记录。

关键词为文字包含匹配，`%`、`_`、引号等按普通文字处理，不安装中文分词依赖。标题上限120字符、正文100,000字符，前后端使用相同Unicode计数；分页默认20/上限100。导出用与检索相同的时间轴语义，单次筛选区间最多366日，另设最多1000篇及20MiB生成体积上限，超限明确提示分段，不静默截断。一致读取快照内每篇只导出一次，并保存entryId、创建/修改时间和可选覆盖范围，不能仅以日期作为文件名；Markdown文件名使用UUID，纯文本下载，不执行HTML，不混入本地未保存草稿。当前阶段不提供历史恢复导入。

### 5. 串行自动保存与明确的未确认状态

工作区复用已安装编辑器，默认编辑区优先、预览可切换，支持手机、写作日历和分页列表。提供独立“新建日记”操作和可留空的内容日期范围；选择列表条目按ID编辑，不把日历日期当作唯一编辑位置。未选择日记时显示新建/选择占位，新建草稿不自动填充或推断覆盖日期。第一版仅文字Markdown，禁止预览主动加载外部图片/嵌入资源，链接使用既有安全规则，不加入公共图片上传按钮。

编辑状态为loading/clean/dirty/saving/failed/offline/conflict/locked。输入停止约2秒自动保存，持续输入最大等待约30秒；每篇日记同一时刻只发送一个写请求，期间修改只合并为下一份最新待保存快照，不无限积压队列。每次出站快照记录本地编辑序号、owner、entryId、内容时间范围、expectedRevision、mutationId；范围修改也属于待保存编辑。

收到有效成功ACK后只更新其对应的已保存基线；若本地已继续编辑或修改时间范围，保留dirty并继续下一次保存。旧请求、其他篇目或旧账号的响应不把当前编辑器标为clean。超时/断连视为结果未知，保留同一entryId、mutationId及完整快照重试以读取幂等结果，不能换ID新建或猜测保存失败；在该快照状态确定前不发送依赖它的新版本。

409 时暂停自动保存，保留本地文字并展示“服务器内容/本地未保存内容”，允许复制/下载本地草稿、重新载入服务器或在明确选择后基于最新版本保存本地内容；禁止自动合并、强制覆盖循环。离线/503 时保留内存草稿和错误提示，可恢复后手动或有界退避重试，不无限重发。

路由/篇目切换或新建另一篇时，在dirty、saving、failed或conflict状态提供“保存后离开/继续编辑/放弃未保存内容”选择；浏览器卸载用标准beforeunload提醒，但不依赖浏览器必然触发提示，也不以sendBeacon卸载写入作为保存承诺。修改覆盖日期不会切换或另建日记，而是当前篇的普通编辑。提供本地草稿下载作为断网退出前的救济。默认不将正文、历史或导出写入localStorage、sessionStorage、IndexedDB、Service Worker或URL。

仅确认的同一前台账号可解锁编辑；认证明确失效时暂停写入并提示重新登录，临时资料请求失败不清除尚待处理的内存草稿。退出登录/身份切换撤销待发送任务、清除编辑器及私密界面，任何晚到响应失效；同账号恢复后先核对服务器版本再继续保存。账号变更不把上一账号草稿带给新账号，不更改全局登录有效期或管理员二次验证。

### 6. 行级隔离与运维边界

应用始终执行 owner 过滤，再对 entry、entry_revision、mutation 启用并 FORCE RLS。运行账号不是表所有者、超级用户或 BYPASSRLS，schema/DDL 权限属于独立迁移账号。每次 PG 事务在绑定的连接使用 `SET LOCAL` 等价的参数化 `set_config` 设置从认证得到的 owner，上下文缺失默认拒绝；提交、回滚及复用连接不遗留上一身份。接口资格检查仍必需，不能把 RLS 当作免认证。

“仅本人”是应用授权边界，不能声称数据库/主机运维者无法读取。PG 不开放公网监听，备份加密并限制访问，秘密仅在外置配置。当前正文不调用云端、不复制进分析服务。

使用版本化、可重复执行且检查既有 schema 兼容性的迁移脚本，迁移事务失败不留下半套结构；不由应用启动自动更改线上 schema，不将 PG DDL 跑到 MySQL。保存采用正常 WAL/持久卷及提交持久化配置（不通过关闭 fsync/synchronous_commit 换性能）。备份须包含正文、历史、墓碑、幂等结果和必要角色/策略重建说明，在隔离新库实际 pg_restore 后验证版本与归属；单有备份文件不算恢复成功。

首阶段不新增定时备份自动化任务；给出手动备份及部署手册，备份频率和保留周期由后续上线配置确定。上线前实测服务器资源，设置连接池/SQL上限；回退通过关闭日记开关并保留 PG 数据，禁止自动删库、清理历史或覆盖旧 MySQL 配置。

参考依据： [Spring Boot 数据源说明](https://docs.spring.io/spring-boot/how-to/data-access.html)（实施时切换到项目对应4.0版本）；[PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)；[PostgreSQL 逻辑备份](https://www.postgresql.org/docs/current/backup-dump.html)。

## Risks / Trade-offs

- [新增 DataSource 影响原自动装配] → 保留明确的 MySQL 主绑定，PG 使用独立 JDBC/事务；开启、关闭和故障状态均跑真实双库验证。
- [已提交但响应丢失导致重复覆盖] → 持久 mutationId 与请求摘要，同事务保存结果；重试原请求，再继续下一份编辑快照。
- [多标签页/删除后迟到保存] → 按稳定日记ID进行持久版本条件更新并保留墓碑；同日不同篇可独立保存，同篇409停止自动覆盖并保留本地内容。
- [浏览器进程终止丢失未确认文字] → 保存状态诚实、自动保存/离开提示/本地下载，不虚称具备离线持久化。
- [RLS 被运行角色或连接复用绕过] → 非所有者低权限角色、FORCE RLS、事务级身份、真实连接池交替身份测试与无上下文拒绝测试。
- [正文泄漏到日志、搜索或浏览器缓存] → 私有路由与读取面清单、按字段记录元数据、请求体/SQL日志检查、no-store、导出下载与 Markdown 预览网络拦截测试。
- [完整历史增长、PG抢占现有服务资源] → 合并连续编辑、无变化不建版本、小连接池、有限查询与资源实测；不静默删除历史。观察后再单独规划保留策略。
- [归档规划与实际源码不一致] → 以当前源码与基线测试核实复用点；不自动重启归档整改，也不把未提交实现假定为完整安全基础。

## Migration Plan

1. 实施前记录分支/HEAD/无关改动，恢复并核实图谱；逐个修改符号 impact，补充登录、日志、双数据源基线。
2. 在隔离 PostgreSQL 创建迁移/运行角色，执行迁移两次和失败注入，跑真实事务、RLS、并发/幂等测试；原有 MySQL 用虚构数据验证不串库。
3. 完成前台编辑、权限、状态机和真实浏览器验收；运行默认后端、前台/后台既有检查与构建，保留原有失败证据，不能用检查通过掩盖未测设施。
4. 实际发布前读取服务器资源与部署配置，说明新增 PG 的资源、目录、端口、备份和回退影响；在日记关闭状态部署，原博客保持可用。
5. 完成隔离恢复演练后，再按独立授权迁移生产、填写实际站主 ID 和秘密并启用；只用站主主动填写的日记做线上验收，不写演示私密内容。
6. 故障关闭日记并回退应用，保留数据与备份；恢复前核对时间点、版本、历史、角色和幂等记录，不自动清空或重新初始化。
