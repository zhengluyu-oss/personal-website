## Context

当前博客聚合页和分类页共用 `Pigeonhole/Category/index.vue`。分类列表由现有公开分类接口加载，分类 slug 在前端稳定映射；右侧统计已按当前分类变化，但左侧 Hero 的眉题、双色主标题和简介仍硬编码。分类实体 `t_category` 已承载分类名称、分类推荐文章等分类级展示配置，因此 Hero 文案继续放在该表能够保持数据归属清晰，也无需新增接口或额外请求。

## Goals / Non-Goals

**Goals:**

- 允许管理员在分类管理中维护每个分类独立的 Hero 左侧文案。
- 分类切换时通过现有分类响应即时更新 Hero 文案。
- 对旧数据、空配置和部分配置提供逐字段默认回退。
- 保持现有 Hero 视觉风格、分类 slug、文章统计、推荐文章和文章列表逻辑不变。
- 提供可备份、可验证、可回滚的数据库迁移。

**Non-Goals:**

- 不让分类配置 Hero 背景、颜色、字号、排版模板或右侧统计文案。
- 不把 `/blog` 全部文章页默认文案迁移到分类表。
- 不新增后端 API 路径，不改变分类或文章路由。
- 不引入富文本编辑器、多语言模型或新的前端依赖。

## Decisions

### 1. 在 `t_category` 保存四个可空字段

字段建议为 `hero_eyebrow`、`hero_title_accent`、`hero_title`、`hero_description`，分别映射眉题、白色强调标题段、浅色标题段和简介。字段均允许 `NULL`，旧数据无需回填即可继续运行。

选择四字段而不是单一 JSON，是因为这些值结构稳定、需要独立长度校验和后台表单回显；显式列也更利于迁移审计。未采用独立配置表，是因为 Hero 与分类是一对一关系，额外表和关联查询没有收益。

建议长度上限：眉题 60、两个标题段各 60、简介 240。数据库列长度、DTO 校验和管理端 `maxlength` 保持一致。

### 2. 复用现有分类接口返回配置

扩展 `Category`、`CategoryDTO` 和 `CategoryVO`，由现有分类新增/更新及查询链路自动传递字段。前端已经先请求分类列表再解析 slug，因此无需把文案重复放进 `BlogFeedVO`，也无需增加一次网络请求。

### 3. 前端逐字段计算有效 Hero 文案

在分类页组件中定义不可变的默认 Hero 文案，并根据 `activeCategory` 计算当前展示值：只有经过 `trim()` 后非空的分类字段才覆盖默认值。逐字段回退支持管理员只定制标题或简介，也避免空字符串造成视觉缺口。

路由切换时计算属性直接基于当前分类，避免把文案复制进异步状态，从而消除上一个分类文案残留。`/blog` 没有活动分类，天然回退到默认对象。

### 4. 管理端在现有分类弹窗中分组编辑

沿用分类新增/编辑弹窗和公共保存接口，在“分类展示文案”分组中放置四个输入项。标题字段使用普通输入框，简介使用多行输入框；全部显示字符计数、长度和“留空使用默认文案”的说明。由于新增分类也需要配置文案，这些字段不依赖分类 ID，可在新增和编辑两种状态显示。

### 5. 数据库迁移先于应用部署

向前迁移新增四个可空列，不添加外键或必填约束。部署前备份 `t_category`，执行迁移并通过 `information_schema` 验证四列存在，再部署后端和前端。回滚时先回滚应用；列可暂时保留，确认旧应用稳定后再删除。

## Risks / Trade-offs

- [自定义标题过长导致 Hero 高度异常] → 前后端统一长度限制，并验证桌面端、平板和手机端接近上限的换行效果。
- [MyBatis 更新策略跳过 `NULL`，导致清空后旧值仍存在] → 分类更新使用显式更新包装器或确认字段更新策略，针对清空场景增加后端测试。
- [分类切换期间显示上一分类文案] → 展示值只从同步的 `activeCategory` 计算，并在未知 slug/分类加载状态下使用默认文案或现有骨架状态。
- [数据库先迁移但应用暂不部署] → 新列可空且不影响旧应用，允许安全分阶段上线。
- [管理弹窗字段增多变得拥挤] → 适当增大弹窗宽度并使用分组、两列桌面布局和单列窄屏布局。

## Migration Plan

1. 备份生产数据库 `t_category` 表。
2. 执行可空字段向前迁移，并验证四列名称、类型和默认值。
3. 部署后端，验证分类新增、更新、清空和公开读取。
4. 部署管理端和博客前端，配置一个测试分类并验证分类切换与移动端布局。
5. 若需回滚，先恢复旧应用；新增可空列暂时保留。确认无依赖后执行删除四列的回滚 SQL。
