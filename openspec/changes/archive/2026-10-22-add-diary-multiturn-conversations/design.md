## Context

`DiaryAiController` 的 `/questions`、`/reviews` 目前只接收一次性请求，`DiaryAiWorker` 为每个任务构造一组 system/user 消息；`diary_ai.job` 和 `diary_ai.report` 没有对话归属。前端 `DiaryAiPanel.vue` 只持有一个当前任务和报告，旧问题仅在内存中关联，刷新即消失。现有 PostgreSQL 私密存储、RLS、全局 worker 租约、向量检索、引文校验、预算与任务终态都应继续使用。站主可生成，按现有模块权限获得只读访问的访客不能发起对话或取得任务载荷。

## Goals / Non-Goals

**Goals:**

- 问答和原文复盘各自从首轮开始形成可恢复的线性对话，站主可以连续追问；每轮有独立问题、回答、状态和引用。
- 每轮仅把经过当前来源校验的日记文字当作个人事实证据；历史模型回答只提供语境，不充当来源。
- 复用现有异步任务、幂等、取消、预算、来源变更和失败诊断机制，不自动重发云端请求。
- 首轮和既有 API 向后兼容；旧报告保持原有阅读路径，不伪造缺失的历史问题。

**Non-Goals:**

- 分支、多人共享、跨对话记忆、自动定时提问、工具调用、流式逐字输出、Python 或新模型服务。
- 期间周/月回顾 `diary_coaching.period_report` 的连续追问及普通访客参与生成；它仍按现有独立报告展示。
- 对历史一轮报告做无根据的对话回填，或让模型自动修改日记、目标与行动。

## Decisions

### 1. 增量对话模型，而非把历史拼到单个报告里

在同一个 PostgreSQL 库新增独立 `diary_conversation.conversation` 与 `diary_conversation.turn`（或等价的规范化表）。`diary_ai` 的版本收据对表数量和结构做校验，不能直接向其增加表。对话绑定 `owner_id`、`kind`（QUESTION/REVIEW）、初始范围和创建时间；轮次按单调序号关联请求、可选 `job_id`、可选 `report_id`、用户输入与状态。所有主外键含 owner，沿用既有私密 schema 的 RLS/连接角色。写入首轮和入队须原子化；`request_id`/请求摘要重复提交必须返回同一轮，不重复计费。只有站主可以列出、读取、创建、追问、取消及删除；对话删除清理派生消息与报告/任务私密载荷，保留既有最小幂等/用量审计要求，不删除原日记。

现有单次 `/questions`、`/reviews` 继续兼容。新对话 API 支持创建首轮、列出/读取对话、提交追问与删除；任务仍由现有 `/jobs/{id}` 或等价状态接口查询，不额外开模型调用。旧报告不自动变成对话；未来若支持导入，须显式迁移并解释旧问题缺失。

### 2. 每轮独立检索和校验

QUESTION 首轮沿用当前语义检索。追问先依据少量有效前文把“那一次”“第二条”明确为本轮独立检索问题，再检索当前日记索引；范围默认沿用对话范围，用户如需换范围应新开对话，以避免无声改变讨论对象。问题改写优先采用确定性上下文拼接；若以后增加单独模型改写，必须纳入用量/费用且不得静默请求。生成提示包含本轮问题、必要的已验证前文摘要、当前证据目录及可引用原文。历史 AI 文字不得被赋予来源 ID，也不得满足引用校验。仍按本轮 `DiaryQuoteCatalog`、`DiaryValidation`、`DiaryAiEvidence` 校验输出，报告来源绑定日记 ID、revision、片段哈希；直接使用服务端保存的原问题和回答构建历史，不信任浏览器提供的历史数组。

REVIEW 首轮保留完整范围预览、snapshotDigest 与结构化报告。后续追问默认仍围绕这份范围：每次重新验证完整范围摘要与来源有效性，再按现有完整范围预算生成有证据的回答；不得以 Top-K 替代完整复盘而仍称完整范围。超出预算时明确要求缩小范围并新建对话。追问的回答可沿用问答结构，但保留复盘首轮的原结构化报告与建议引用。两种对话均串行：上一轮非终态时拒绝/阻止下一轮提交。

### 3. 有界历史与失效策略

仅携带最近若干轮的必要用户问题、成功且仍有效的 AI 结论，按当前提示字符预算动态裁剪；对较早轮次使用服务端构建的有界摘要或明确省略，界面仍展示全部已保存轮次。摘要不得新增个人事实或作为证据。当前来源目录和系统规则优先占预算，输入超限在发送前拒绝，不静默裁剪必需复盘证据。

日记修改、删除或范围成员变化后，相关轮次按既有报告失效规则标记 STALE 并隐藏派生正文/引文；历史用户问题、时间和任务状态可保留。后续追问须重新验证对话锚点，若锚点或必要前文已失效，拒绝继续并引导站主重新预览/新建对话；绝不把旧答案放进新提示。源变更时的迟到模型结果不得发布。

### 4. 前端以线性消息时间线承载任务

“问日记”和“做复盘”各有对话列表、新建入口和当前消息时间线。每轮显示“你的问题/首轮复盘范围 → 处理中/回答/失败 → 本轮引用来源”；底部追问输入只在上一轮终态且来源有效时启用。用户刷新后由服务端恢复问题、任务状态和回答；轮询只查询现有任务，不重复提交。取消、失败、未知结果和可能计费提示留在对应轮次，人工重试必须生成新请求。引用仍可定位到当前原文；移动端保持输入与结果清晰分区。

## Risks / Trade-offs

- [私密内容进入新表和日志] → 扩展 RLS/owner 检查、no-store、不记录正文或模型提示；验证只读访客和伪造 owner 都不能访问对话 API。
- [多轮历史挤占上下文，导致费用或截断] → 有界轮数和字符预算，当前证据优先，每轮沿用每日20次生成尝试、队列5和输出上限；UI提交前提示每轮可能计费。
- [历史结论和新日记冲突] → 来源版本失效与新轮检索，历史 AI 文字不得当引用；锚点过期时引导新对话。
- [数据库部署与旧版应用兼容] → 仅新增表/索引和 API，先迁移再部署；保留旧接口，回滚应用时新表可留存但不可见，不删除生产数据。
- [任务完成与对话轮次写入不一致] → 入队与轮次事务化，完成/失败时按 job_id 幂等关联，恢复任务后可重建轮次状态；压测并发重复提交与崩溃恢复。

## Migration Plan

1. 在测试 PG 验证增量 schema、RLS、所有权、备份恢复和旧报告兼容；生产先做可恢复备份，再执行向前兼容迁移。
2. 发布后端并保持新对话入口关闭，验证旧问答/复盘、额度、任务状态、删除与来源失效，再打开新入口。
3. 发布前端，按真实站主账号验收问答与复盘多轮、刷新恢复、失败/取消、引用变化及手机布局；只读账号验收不能生成或读取私密任务。
4. 回滚时先关闭新入口再回滚前后端；保留新表数据与旧接口，不自动清空对话。失败任务仍遵守不自动重发。

## Open Questions

无阻塞性问题。实施时通过受控测试确定最合适的历史轮数/摘要字符默认值，并作为可调内部参数，不改变上述安全边界。
