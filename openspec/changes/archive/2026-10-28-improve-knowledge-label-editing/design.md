## Context

知识库后台的“分类与标签”区域目前在折叠面板中列出已有分类和标签。`改名`调用 `window.prompt`，而标签的“保存归属”是另一项操作；两者共用 `manageLabel`，改名时还会读取尚未保存的所属分类草稿。服务端已有带 `expectedRevision` 的 `POST /knowledge/manage/labels` 更新能力，分类或标签 ID 被条目引用，名称本身不是关联键。

## Goals / Non-Goals

**Goals:**

- 让站主能在知识库后台明显地找到并完成已有分类、标签的全局名称编辑。
- 保存名称时保持 ID、类型和标签所属分类不变，使全部关联条目自动显示新名称。
- 在表单内处理输入校验、保存状态、重名和版本冲突，并支持取消。

**Non-Goals:**

- 不改变某篇条目的分类或标签选择，也不批量迁移条目。
- 不重新设计博客文章后台的分类、标签页面。
- 不改变现有新增、删除或标签所属分类调整的业务规则。

## Decisions

1. **使用页面内的明确编辑表单。** 每行保留可见的“编辑名称”按钮；点击后展示当前名称、分类/标签类型、全局影响说明以及“保存”“取消”。比浏览器原生提示框更易发现，也能在同一位置显示错误。考虑过单独弹窗；本区域已有简洁的行式管理布局，页内表单更符合现有结构且无需新依赖。
2. **复用现有更新接口与版本号。** 提交原 `id`、`kind`、`expectedRevision`，只改变 `name`；标签重命名一律发送服务端已保存的 `parentCategoryId`，不采用尚未保存的归属草稿。这样重命名不会意外移动标签。无需数据库迁移或修改条目外键。
3. **区分校验与并发失败。** 客户端阻止空白、超过 80 字、同类型重名和未变化的提交；服务端在现有更新路径对同类型重名给出明确冲突结果，并继续用版本号拒绝过期提交。失败时保留用户输入，提示重新核对；成功后重新读取标签与相关条目视图。考虑过仅做客户端校验，但无法覆盖另一个会话同时改名的情况。
4. **维持站主权限边界。** 编辑入口仅在 `canManage` 时出现，写入仍由 `requireManage` 校验。前台知识库只读取更新后的名称，不增加写入入口。

## Risks / Trade-offs

- [已有关联条目的显示名称同时变化，用户可能误认为条目被移动] → 表单说明这是全局改名且不改变归属；保存后保留当前筛选的 ID。
- [改名与标签归属草稿并存时发生意外移动] → 改名请求只使用标签当前已保存的父分类 ID，并将“保存归属”作为独立操作。
- [并发修改或重名导致保存失败] → 保留输入、显示具体错误；版本冲突时刷新最新标签信息，由用户重新确认后再保存。

## Migration Plan

仅发布后台前端及必要的服务端错误处理改动，不迁移数据。验证现有分类和标签改名后 ID 与关联数量不变；若需回退，回滚发布产物即可，已保存的名称仍是有效数据，可通过同一接口再次改名。
