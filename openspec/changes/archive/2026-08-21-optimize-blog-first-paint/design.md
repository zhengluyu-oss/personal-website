## Context

线上抽样显示网站信息、Banner 和文章接口均在约 30–60ms 内响应，Banner 图片约 257KB，也不是主要瓶颈。真正阻塞 Vue 挂载的是首页初始依赖：约 2.55MB 的 vendor JavaScript 未以 gzip 交付，在 3Mbps 服务器带宽下需要约 6–8 秒；另有约 419KB 的依赖 CSS。当前 Vite 虽启用了压缩插件，但压缩文件没有在实际资源旁被 Nginx 命中，线上响应没有 `Content-Encoding`。

应用还把网站信息和 Banner 请求纳入全屏 Loading，而 HTTP 错误拦截器没有执行与成功路径等价的计数释放。公开站点入口始终挂载反调试组件，可能增加主线程阻塞和误判。改动横跨构建、应用启动、请求状态和 Nginx 部署，因此需要统一设计与可回滚验收。

## Goals / Non-Goals

**Goals:**

- 在 3Mbps 受控网络下显著缩短从打开首页到看到稳定首屏的时间。
- 保证生产静态资源实际以压缩形式交付，而不只是生成未被使用的 `.gz` 文件。
- 减少首页初始 JavaScript/CSS，非首屏功能按需加载。
- 让页面框架优先渲染，并保证 Loading 在所有请求结果下都能恢复。
- 用构建预算与部署探针把性能要求变成可重复验证的门槛。

**Non-Goals:**

- 不调整数据库模型、接口协议或文章查询业务逻辑。
- 不重做已经确定的首页视觉语言、Banner 内容或后台信息配置能力。
- 不引入 CDN 作为本次落地前提；CDN 可在后续作为进一步优化。
- 不以牺牲核心可访问性或删除用户可见功能来换取指标。

## Decisions

### 1. 先修复传输链路，再进行依赖拆分

压缩插件继续生成与原文件相邻的 `.gz` 文件，修正会产生绝对路径嵌套的输出配置；Nginx 使用 `gzip_static on` 优先返回预压缩文件，并启用动态 gzip 作为缺失预压缩文件时的兜底。对带哈希资源设置长期 immutable 缓存，对 `index.html` 使用重新验证策略，响应加入 `Vary: Accept-Encoding`。

选择 gzip 是因为现有构建已具备插件且 Nginx 通常无需额外模块。Brotli 压缩率更高，但是否具备服务器模块尚不确定，不作为验收前提；确认模块可用后可以并行增加 `.br`。

### 2. 以入口依赖图为依据拆包，不按每个包机械拆分

保留路由和功能组件的动态导入边界，由 Rollup 根据真实依赖图自动安排共享分块；音乐播放器、上下文菜单增强、编辑器、图表和反调试能力仅在对应功能启用或页面到达后加载。构建分析器只在显式分析模式启用，避免生产构建自动打开窗口。

不采用“每个 node_modules 包一个 chunk”或按框架内部模块强制分块，因为前者会制造大量请求和依赖瀑布，后者会在当前 Vue/Element Plus 依赖图中产生循环初始化风险。最终是否属于初始链路由构建 manifest 和预算脚本判定。

### 3. 使用可见应用壳与局部骨架取代接口驱动的全屏门禁

应用入口不再依赖网站信息请求完成后才可见。导航、Banner 容器、标题降级值和页面背景随 Vue 入口立即渲染；网站信息、Banner 和文章列表各自维护局部 pending/error 状态并渐进填充。全局进度条可作为轻量反馈保留，但公开首页数据请求不再锁定 body 滚动或覆盖整页。

保留短暂全屏 Loading 仅适用于真正不可并行的显式操作，而不是普通页面读取。相比设置固定超时强行隐藏，这一方案在慢网下不会出现“遮罩消失但页面仍为空”的假恢复。

### 4. 请求跟踪以单次请求元数据闭环

请求拦截器在 Axios config 上记录本次请求是否启动了进度条/Loading 以及对应键；成功和错误拦截器共用一个幂等 finalize 函数。函数只释放当前请求，不清空其他路径的整个 Map，并在计数归零时恢复 body 与进度条。取消、超时和无 response 的网络错误也使用同一路径。

选择请求级标记而不是仅按 URL 的 `firstRequestPaths` 永久去重，可避免第一次失败后后续请求永远不再正确跟踪，也便于编写并发测试。

### 5. Banner 使用确定尺寸、优先提示和安全降级

唯一 Banner 的容器使用响应式 `aspect-ratio`/最小高度预留空间，实际首图使用 `fetchpriority="high"`，并在可于 HTML 阶段确定 URL 时增加 preload；若 URL 只能由接口返回，则在拿到 URL 后立即加载，不等待非关键文章数据。图片失败时显示现有视觉体系的渐变背景与可读标题。

不把大图内联成 base64，因为会扩大入口 HTML、失去独立缓存，并推迟 HTML 解析。

### 6. 反调试能力默认关闭并脱离首屏

公开生产配置默认不挂载反调试组件；如站点所有者明确启用，则通过动态导入在首屏稳定后加载。前端反调试不能保护已下发代码，却可能阻塞浏览器、自动化检查及求职访问者，因此不应成为默认性能成本。

### 7. 预算检查同时覆盖构建和线上

构建阶段读取 Vite manifest/产物，计算首页初始依赖及 gzip 体积，执行 700KB 初始 JS、180KB 初始 CSS、450KB 单 JS 分块预算。部署后用真实 URL 检查状态码、`Content-Encoding`、缓存头和资源体积，并在冷缓存、移动视口、约 3Mbps 条件下记录 FCP/LCP/CLS。首次实施先保存改造前基线，再以规范阈值作为最终门槛。

## Risks / Trade-offs

- [拆包过细引入额外网络往返] → 限制共享分块数量，并依据 manifest 与瀑布图合并高频共同依赖。
- [预压缩文件与源文件版本不一致] → 每次构建同时生成，部署阶段校验时间戳/内容并以原文件动态 gzip 兜底。
- [缓存策略导致旧入口引用已删除资源] → `index.html` 不长期缓存，部署保留上一版本静态目录直到健康检查通过。
- [局部骨架改变现有 Loading 视觉] → 复用现有设计 token，在移动端、弱网和错误态做截图验收。
- [严格预算可能被合理新功能触发] → 预算变更必须在独立评审中说明原因，不允许部署脚本静默跳过。
- [3Mbps 环境存在网络抖动] → 传输体积和响应头作为确定性门槛，Web Vitals 连续运行多次并取中位数。

## Migration Plan

1. 记录当前线上关键资源、响应头、构建依赖图和冷缓存性能基线。
2. 修复请求 finalize 与可见应用壳，增加错误和并发测试，先消除永久白屏风险。
3. 调整动态导入和分块策略，加入构建预算，确认核心页面功能与视觉回归通过。
4. 修复 gzip 产物位置并更新 Nginx 配置，在服务器暂存目录验证配置和压缩响应。
5. 原子切换静态版本，运行首页、接口、压缩、缓存和受控网络检查；全部成功后完成部署。
6. 若健康或视觉检查失败，切回上一版静态目录并恢复上一份 Nginx 配置后重新加载。

## Open Questions

- 服务器当前 Nginx 是否编译了 Brotli 模块；该信息只决定是否追加 Brotli，不阻塞 gzip 方案。
- Banner URL 是否能在入口 HTML 生成阶段获知；若不能，则采用接口返回后的高优先级加载而不生成无效 preload。
