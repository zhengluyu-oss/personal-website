## Context

博客前台与管理员端是两个独立的前端应用。博客前台使用 `Token` 键及 `{ token, expire }` 数据，并根据用户信息决定导航栏展示；管理员端使用 `Authorization` 键及 `{ token, expires }` 数据。生产部署虽可能处于同一站点的不同路径，但不同存储键和会话约定不会自动同步。博客前台未勾选“记住我”时使用 `sessionStorage`，令牌仅在当前标签页会话中保留。

## Goals / Non-Goals

**Goals:**

- 确保博客前台登录成功后，令牌可被后续请求读取，用户信息成功恢复后导航立即显示登录状态。
- 刷新博客页面后恢复有效会话；令牌过期、损坏或用户信息加载失败时清理前台会话并提供明确状态。
- 保持后台与博客前台身份会话独立，避免隐式将管理员令牌暴露给普通前台应用。

**Non-Goals:**

- 不在管理员端登录后自动登录博客前台。
- 不更改后端认证 API、令牌权限或角色授权规则。
- 不改变“记住我”关闭时令牌只在当前标签页有效的安全语义。

## Decisions

- **以博客前台自己的令牌键作为唯一前台会话来源。** 登录、请求拦截器和启动时用户信息恢复统一通过认证工具读写 `Token`，防止各处采用不同存储约定。
- **令牌解析失败时安全清理并返回未登录。** `GET_TOKEN` 应处理无效 JSON、缺少字段和过期值，不能因解析异常中断页面渲染或请求初始化。
- **用户信息是导航登录态的依据。** 初始化和登录完成后都请求当前用户信息；成功时更新响应式用户状态，失败时清理令牌与用户状态，避免令牌存在但导航仍呈现匿名状态。
- **管理员端令牌不做自动迁移。** 管理员端与前台虽然共享站点源的浏览器存储空间，但键名与生命周期不同；自动复用会扩大管理员凭据在公开前台 JavaScript 环境中的使用范围。需要前台登录时应通过前台登录流程建立会话。
- **域名维持浏览器默认隔离。** `www.zhengluyu.com` 与 `zhengluyu.com` 是不同来源，不尝试跨主机读写浏览器存储；生产环境统一使用规范域名访问。

## Risks / Trade-offs

- [会话状态仍受来源域名影响] → 统一网站链接和登录跳转使用规范主机名，并在文档或界面提示不要在裸域与 `www` 之间切换。
- [用户可能期待后台登录自动关联前台] → 前台保持独立认证，并明确需要在博客登录入口单独建立会话。
- [存储损坏后会退出登录] → 这是令牌不可安全解析时的预期行为；展示可理解的重新登录提示。

## Migration Plan

无需数据库或后端迁移。发布前台静态资源后，用户在博客登录入口重新登录即可建立符合新逻辑的会话；回滚时恢复旧前端资源即可。

## Open Questions

- 若用户实际希望后台登录后前台也自动登录，需要另行设计有明确授权边界的单点登录流程；本变更不启用令牌跨应用复用。
