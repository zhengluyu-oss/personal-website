# 文章分页发布与回滚说明

## 发布顺序

本次分页调整不修改数据库结构，也不新增依赖。由于管理端文章接口的响应由数组升级为分页对象，发布时必须遵循以下顺序：

1. 备份当前后端、博客前端和管理端构建产物，并记录当前版本号或提交号。
2. 先发布后端，确认文章公开聚合接口和管理端文章列表接口返回分页总数。
3. 再发布博客前端，验证 `/blog`、`/blog?page=2` 与 `/blog/:slug?page=2`。
4. 最后发布管理端，验证文章列表默认每页 10 条，并可切换为 20、50 条。
5. 清理或刷新静态资源缓存，确保浏览器不会混用新旧前端资源。

后端发布完成、前端尚未发布的短暂窗口内，旧管理端可能无法正确读取文章列表。因此三部分应安排在同一个发布窗口内连续完成。

## 发布后检查

- 全部文章与分类文章的推荐文章不重复出现在普通列表中。
- 第一页地址不包含 `page=1`，第二页及以后使用 `?page=N`。
- 非法页码与超过末页的页码会自动回到有效页面。
- 管理端搜索、重置、刷新、切换页码和每页条数均保持正确总数。
- 删除末页最后一条记录后自动回退到上一页。
- 桌面端和移动端均有加载反馈，分页控件不横向溢出。

## 回滚方案

分页接口契约与两套前端必须作为一个整体回滚：

1. 先恢复上一版本的博客前端和管理端静态资源。
2. 随即恢复上一版本后端。
3. 清理静态资源缓存并重新验证公开博客和管理端文章列表。

不要只回滚后端或只回滚管理端，否则管理端可能因数组与分页对象的响应结构不一致而无法显示文章。此次变更没有数据库迁移，回滚不需要执行数据库脚本。
