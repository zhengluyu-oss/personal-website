## 三十三、分布式锁：拿到锁只是第一步

多个服务实例要互斥处理同一订单时，可用一个带过期时间的键做租约。加锁使用唯一随机值，而不是固定的 abc123：

    SET lock:order:1001 <随机持有者令牌> NX PX 30000

NX 让同时竞争者中只有一个成功，PX 给锁设定 30 秒过期时间，避免进程崩溃后永久占用。业务结束时只能释放自己持有的锁。先 GET 判断、再 DEL 是两个命令，中间可能发生过期和新持有者接管；需使用原子条件删除，例如受支持版本的条件删除能力或 Lua 脚本。Redisson 等库可封装续租与释放，但调用方仍要理解锁的有效期、重试和失效场景。

锁过期后，旧持有者仍可能继续执行。这时两个实例可能同时写入下游系统。对不能容忍这种情况的业务，要让下游校验递增的 fencing token 或使用数据库条件更新等权威约束；单靠 Redis 锁不能自动保证外部副作用只发生一次。

### 消息队列：List 与 Stream 的取舍

普通 List 的 LPUSH/BRPOP 入门简单，但消费者取走消息后宕机时，消息可能丢失；需要自行设计确认、重试、积压控制。Stream 提供追加、消费组、待确认列表和确认命令：

    XADD orders * orderId 1001
    XGROUP CREATE orders workers 0 MKSTREAM
    XREADGROUP GROUP workers consumer-1 COUNT 10 STREAMS orders >
    XACK orders workers <消息ID>

消费成功后才 XACK；失败消息仍需制定重试和死信规则。Stream 也不是“恰好处理一次”保证：消费者崩溃、重领待确认消息或确认失败，都可能导致重复处理。业务处理必须幂等，并给 Stream 设置合理保留策略，监控长度、消费延迟和待确认数量。

### 选型问题

先问是否允许丢消息、是否需要重放、消费者规模、消息体大小、积压时长和跨系统事务。简单通知可用较轻方案；关键业务任务要评估专门消息系统或持久化任务表，并做故障演练。不要因已经部署 Redis 就自动把所有异步任务放进去。

## 三十四、锁失败时系统应该做什么？

抢不到锁不是异常的全部含义：也可能是另一个实例正在处理相同订单。接口应根据业务返回“稍后重试”、排队或幂等地返回既有处理结果。不要在循环里毫无间隔地重试；这会把锁服务变成热点。重试需设置次数、退避和总超时，并记录竞争率与持锁时长。

锁的 TTL 应覆盖正常业务耗时，同时不能无限长。若任务可能运行很久，续租必须确认自己仍是持有者；一旦续租失败，旧执行者应停止后续可停止的工作。若已对外部系统发出不可撤销操作，仍需外部幂等键或数据库唯一约束来兜底。锁保护的是并发进入，不等于业务事务。

单实例 Redis 锁依赖该实例的故障语义。主从复制通常是异步的：主节点确认锁后、复制给从节点之前宕机，从节点提升时可能不知道这把锁。因此对严格互斥的核心业务，必须评估故障切换窗口和权威存储约束。Redisson 或 Redlock 等实现也不能替代对失败模型的说明。

## 三十五、Stream 消费组的完整处理循环

生产者 XADD 后，消费组中的一个消费者用 XREADGROUP 读取。读到消息并不等于处理完成；确认应发生在业务处理成功之后。若消费者崩溃，消息会留在待确认列表，其他消费者需要用相应的重领机制接管。接管后同一消息可能再次执行，因此处理端要保存业务幂等标识。

设计一个订单事件处理器时，至少记录以下字段：消息 ID、业务订单 ID、重试次数、首次失败时间、最后错误类别。只有解析成功且业务提交成功后才确认；永久失败进入人工可见的失败队列或状态表；短时网络失败有限次重试。Stream 的保留上限不能短到未处理消息还在等待时就被清理，也不能无限增长。

### 对比三种模型

| 模型 | 消费者收到后宕机 | 适合用途 |
| --- | --- | --- |
| List 的 BRPOP | 已弹出的消息通常需要自行恢复 | 简单、可丢的临时任务 |
| Stream 消费组 | 可检查待确认消息并重领 | 需要确认和重试的事件流 |
| 专用消息中间件 | 依产品配置实现确认、路由和持久化 | 复杂路由、跨服务积压与治理 |

以上是设计维度，不是“Stream 保证绝不丢消息”的承诺。Redis 本身的持久化和复制设置、生产者写入确认、消费者幂等与监控都要一起考虑。
