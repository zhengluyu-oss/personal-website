## 三十六、把学习路线变成可验证的练习

只记术语不容易发现理解缺口。每个阶段都应能运行命令、解释返回值，并说出故障时的处理方式。

| 阶段 | 动手练习 | 合格的解释 |
| --- | --- | --- |
| 基础类型 | 用 String、Hash、Set、ZSet 实现文章详情、用户字段、标签和榜单 | 为什么不把所有数据放进同一结构 |
| 生命周期 | 设置 TTL、覆盖键、观察 -1/-2、配置内存上限 | 过期和淘汰的差别 |
| 持久化 | 在隔离实例验证 RDB/AOF 与重启恢复 | 数据丢失窗口、备份位置 |
| 缓存 | 实现读回源、写删缓存和空值缓存 | 并发回填旧值、穿透/击穿/雪崩 |
| Java 实战 | 用 StringRedisTemplate 完成带 TTL 的缓存 | 序列化、连接失败和回源容量 |
| 进阶 | 用 Stream 消费组处理一条可重试任务 | 确认、重复处理和积压监控 |

### 五道值得完整回答的问题

1. 为什么 SET key value 与 EXPIRE key 60 分两次调用有风险？答题要说明两次命令之间失败会留下无 TTL 键，并给出 SET key value EX 60。
2. 缓存命中率很高，数据库为什么仍可能被打满？答题要考虑单个热点 key 击穿、批量失效、回源并发和数据库连接池。
3. 开了 AOF 是否能保证绝不丢数据？答题要说明刷盘策略、故障类型、备份和恢复演练。
4. SET NX PX 成功后是否一定能安全修改外部数据库？答题要说明租约过期、旧持有者继续执行和下游条件约束。
5. XREADGROUP 取到消息后立刻 XACK 会怎样？答题要解释业务处理失败时消息无法按待确认记录重试，以及至少一次处理需要幂等。

### 一份小型自测方案

在本地隔离 Redis 创建 20 个带随机 TTL 的缓存键；实现一个模拟数据库查询计数器；同时发起多个请求访问同一热点键；记录数据库被访问的次数。然后让 Redis 不可用，再观察接口延迟、错误与数据库负载。最后检查恢复后的数据和监控。这个练习比死记“缓存击穿要加锁”更能说明锁失败、超时和降级的代价。

学习时优先掌握常用命令的返回值和边界，再看集群、复制、Sentinel 与源码。任何“推荐配置”都应结合当前版本、业务丢失容忍度和可用内存验证，不宜照抄面试答案到生产环境。

延伸阅读：[Redis 官方文档](https://redis.io/docs/latest/) · [Spring Data Redis](https://docs.spring.io/spring-data/redis/reference/)
## 三十七、从面试题走向故障诊断

面试题的价值在于能解释真实现象。例如“Redis 为什么快”应能指出内存、数据结构和命令执行路径，同时说明大 key、慢命令和网络会使 P99 变差。“缓存雪崩是什么”应能看出大量键同一时刻失效或 Redis 不可用导致回源激增，并区分单个热点 key 的击穿。

可给自己做一张故障卡片：

| 现象 | 先查什么 | 避免的误判 |
| --- | --- | --- |
| 数据库 QPS 突增 | 缓存未命中、过期分布、Redis 错误率 | 只看平均命中率 |
| Redis 内存告警 | used_memory、淘汰计数、大 key | 直接加大 maxmemory |
| 请求 P99 升高 | 慢命令、大返回值、网络与回源 | 断言“Redis 一定很快” |
| 重启后数据缺失 | 持久化状态、备份、恢复时间点 | 认为开启 AOF 就零损失 |
| 队列重复处理 | 待确认消息、确认时机、幂等键 | 认为 XACK 前只会投递一次 |

### 进阶学习顺序

单实例的数据类型与生命周期熟练后，再学习复制与故障切换；之后学习 Sentinel 和 Cluster 的职责、槽位与跨槽操作限制。每一步都在隔离环境做一次故障演练。比如主节点断开时，观察客户端多久恢复、有哪些写入未出现在新主节点，而不只是背诵“主从复制提高可用性”。

最后，把每个知识点写成“命令示例、适用场景、失败模式、验证方法”四栏。这样的笔记会比只有定义和术语列表更容易迁移到实际项目中。
