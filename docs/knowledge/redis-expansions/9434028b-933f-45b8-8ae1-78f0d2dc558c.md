## 十三、用一组业务需求练习选型

假设要实现文章详情缓存、浏览次数、标签、最近评论和热度榜。按访问与更新方式选择结构，不必把所有内容塞进一个大 JSON：

    SET article:detail:1001 '{"title":"Redis 入门"}' EX 300
    INCR article:view:1001
    SADD article:tags:1001 redis backend
    LPUSH article:comments:1001 '评论A'
    LTRIM article:comments:1001 0 49
    ZINCRBY article:rank 1 article:1001

详情缓存可以过期重建；浏览量需要决定何时汇总到权威存储；List 要限定长度；ZSet 的分数算法由业务定义。这里的命令只是结构示例，不能代替完整的一致性与并发设计。

### String：条件写入和计数

SET key value EX seconds 把写入与过期设置放在同一条命令中，避免先 SET 再 EXPIRE 之间崩溃留下永久键。NX 仅在键不存在时写入，XX 仅更新已存在的键。INCR 对一个整数键原子递增；“先检查额度，再递增”是两个命令，整体并不会自动变成原子操作。

### Hash：局部字段更新

    HSET user:1001 name Zhang age 20
    HGET user:1001 name
    HMGET user:1001 name age
    HINCRBY user:1001 age 1

Hash 适合按字段读取，但字段之间没有关系型数据库的外键约束。若对象很大，HGETALL 会一次返回全部字段，需注意响应体与内存。是否使用 Hash 而非 JSON 字符串，取决于局部读写频率、序列化约定和缓存失效方式。

### List、Set、ZSet 的区别

List 保持插入顺序、允许重复，适合有界的最近记录。Set 不保证读取顺序，适合去重和成员判断。Sorted Set 的成员唯一、带分数，适合按分数排序：

    SISMEMBER article:tags:1001 redis
    ZRANGE article:rank 0 9 REV WITHSCORES

普通 List 的 LPUSH/BRPOP 不会自动提供消息确认、失败重试和死信处理。消费者可能宕机且消息不能丢时，应评估 Stream 或专门的消息系统。

### Key 扫描与生命周期

    EXISTS article:detail:1001
    TYPE article:rank
    TTL article:detail:1001
    SCAN 0 MATCH article:* COUNT 100

SCAN 返回下一轮游标，须迭代到游标回到 0。COUNT 是工作量提示，不保证恰好返回 100 个结果；数据变化时也不能把扫描当成强一致快照。生产环境不要用 KEYS * 扫描大库。

练习：为“用户一天最多点赞一次”设计键和 TTL，再说明跨天边界、撤销点赞、持久化和重复请求如何处理。业务规则往往比选一个数据类型更难。

## 十四、常见返回值与误区

EXISTS 返回存在的键数量，不是布尔值。TTL 返回剩余秒数，-1 表示存在但永不过期，-2 表示不存在。SET 带 NX 时，键已存在通常不会写入成功；调用方要检查结果。INCR 遇到不能解析为整数的字符串会报错，不会自动把任意文本转换成 0。

删除前先考虑键的大小。DEL 删除大集合可能增加阻塞；UNLINK 可在适用版本和场景中把实际内存回收交给后台。生产删除应限定明确的 key 范围，先确认数量，避免把示例里的通配符直接用于在线清理。

Set 的交集并非总是“随便做都很快”。两个极大的集合求交集可能消耗 CPU、网络和内存。ZSet 也不应该无限增长：排行榜通常只需要前 N 名或一个时间窗口，历史成绩另行归档。

### 练习：实现最近访问记录

按用户维护一个最多 20 条的最近记录：

    LPUSH user:1001:recent article:12
    LTRIM user:1001:recent 0 19
    EXPIRE user:1001:recent 86400

这三条命令没有自动形成一个整体事务；若需要保证长度与 TTL 同步设置，可用事务或脚本实现。在允许短暂偏差的普通缓存场景，也可以接受分步执行。先写清楚一致性要求，才能决定是否需要更复杂的实现。

### 练习：实现标签筛选

对每个标签保存文章 ID 的 Set，查询两个标签共同文章可用 SINTER。但文章删除或标签变更时，多个 Set 都要同步维护。若需要复杂排序、全文检索与分页，权威数据库或搜索系统可能更适合。Redis 结构解决了某种访问模式，不会自动解决全部查询需求。
