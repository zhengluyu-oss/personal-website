## 十七、过期与淘汰是两件不同的事

过期由业务设置存活时间；到期后键在读取时视为不存在，并通过被动访问或后台主动抽样逐步清理。淘汰发生在设置了 maxmemory、内存达到上限且需要腾出空间时，Redis 依据 maxmemory-policy 选择候选键。带 TTL 的键可能提前被淘汰；未设置 TTL 的键也可能被 allkeys 策略淘汰。

    SET login:code:1001 9527 EX 300
    TTL login:code:1001
    PERSIST login:code:1001
    TTL login:code:1001

最后一次 TTL 返回 -1，因为 PERSIST 移除了过期时间。普通 SET 覆盖已有键时也可能改变 TTL；更新缓存时应明确设置新 TTL，不能假定旧 TTL 自动保留。

### 常见策略怎么选

| 策略 | 候选键 | 适用判断 |
| --- | --- | --- |
| noeviction | 不主动淘汰 | 无法写新数据时允许返回错误 |
| allkeys-lru | 全部键 | 最近访问变化较快的纯缓存 |
| allkeys-lfu | 全部键 | 长期热点明显的纯缓存 |
| volatile-lru | 仅带 TTL 的键 | 混放缓存与不希望被此策略淘汰的键 |
| volatile-ttl | 仅带 TTL 的键 | 倾向先移除剩余 TTL 较短的键 |

LRU/LFU 是近似策略，不是对整个库精确排序。volatile 策略没有可用的带 TTL 键时，可能像 noeviction 一样拒绝写入。还应预留复制、AOF 缓冲区等内存，不能把 maxmemory 直接设为机器全部可用内存。

### 排查内存问题

1. 用 INFO memory 看使用量与峰值；确认 CONFIG GET maxmemory 和 CONFIG GET maxmemory-policy。
2. 用 INFO stats 看命中、未命中和淘汰计数。淘汰持续增加，要检查容量、TTL 与访问模式。
3. 检查无界 List、超大 Hash、大字符串和热 key。少量大 key 也能造成内存和延迟问题。
4. 区分“键到期”和“内存淘汰”；前者看 TTL 分布，后者看内存上限、策略与淘汰计数。

验证码和会话等有安全语义的键必须有明确 TTL，并处理键提前消失、Redis 不可用与重复提交，不能只依赖内存淘汰。

延伸阅读：[键过期机制](https://redis.io/docs/latest/commands/expire/) · [内存淘汰策略](https://redis.io/docs/latest/develop/reference/eviction/)
## 十八、TTL 设计要跟着业务走

详情页缓存可以容忍几分钟陈旧，权限撤销和支付状态通常不行。先写明可接受的最长旧值时间，再设置 TTL，而不是全站统一“缓存 30 分钟”。对同一批任务生成的大量 key，给 TTL 加少量随机抖动可降低同一时刻集中过期的回源峰值。随机范围也应纳入最长陈旧时间计算。

业务主动删除与自然过期也不同：修改商品价格后删除详情缓存，是为了尽快不再返回旧价格；即使设置了五分钟 TTL，也不应只等自然过期。删除失败要有监控和补救。反过来，TTL 到期前也可能因内存淘汰提前消失，所以调用方要能安全回源或失败。

### LRU 与 LFU 的直观例子

假设 A 在过去一小时被访问一万次，但最近十分钟无人访问；B 只访问十次，却刚刚被访问。LRU 更看重最近访问，可能保留 B；LFU 更看重历史频率，可能保留 A。真实 Redis 的算法是近似实现，并带有取样或衰减行为，不能用这个例子推导某个 key 一定被淘汰。

使用 INFO stats 查看 evicted_keys 和 keyspace_hits/keyspace_misses 的变化趋势。命中率应结合请求总量：99% 命中率在每秒十万次请求下，仍可能有每秒一千次回源。若同一实例混放缓存和登录状态，需要评估一类键的内存增长是否挤压另一类键；重要状态不应依赖“缓存策略大概不会淘汰它”的猜测。
