## 二十一、持久化配置怎样影响数据丢失窗口？

RDB 保存某一时点的快照，故障恢复后可能丢失最后一次成功快照之后的写入。AOF 记录写命令；丢失窗口取决于刷盘策略，不能笼统说“AOF 一定不丢数据”。appendfsync everysec 通常意味着约一秒级未刷盘写入的风险；always 增加刷盘开销。磁盘、文件系统和故障类型也会影响结果。

示例配置，变更前应确认当前 Redis 版本和部署方式：

    appendonly yes
    appendfsync everysec
    save 300 100

save 300 100 表示 300 秒内至少发生 100 次写入时满足一次快照触发条件，不代表每 300 秒必定生成快照。临时修改运行时配置后，还要确认配置文件或服务编排中的设置，否则重启可能回到旧配置。

### AOF 重写不是复制旧日志

AOF 长期追加会增长。后台重写根据当前数据集生成更精简的恢复内容，新写入仍需妥善记录。重写会占用 CPU、磁盘 I/O 和额外内存；数据量大时要关注 fork 延迟及写时复制开销。Redis 7 及以后 AOF 文件组织与旧版本不同，运维时以实际版本的目录和配置为准，不假定只有一个 appendonly.aof 文件。

### 恢复检查清单

1. 定义恢复目标：允许丢失几秒、几分钟，还是必须由权威数据库重建。
2. 检查 INFO persistence 的最近 RDB/AOF 结果及后台任务状态。“开启配置”不等于最近一次持久化成功。
3. 把备份放在 Redis 实例之外，并在隔离环境演练恢复。同机复制文件防不了整机或磁盘故障。
4. 恢复后核对关键业务数据与应用行为，不只看进程启动和 PING。

如果 Redis 只做可重建缓存，可以选择较轻的持久化方案；如果保存难以重建的数据，应把复制、备份、故障切换和恢复演练一起设计。RDB 与 AOF 可同时启用，但都不能替代异地备份和业务一致性校验。

延伸阅读：[Redis 持久化官方指南](https://redis.io/docs/latest/management/persistence/)
## 二十二、不要把快照与备份混为一谈

RDB 文件是一份可恢复快照，但如果它只在运行服务器的同一块磁盘上，磁盘损坏时仍可能同时失去服务和快照。备份策略应明确频率、保留期、异地副本、加密和恢复演练。AOF 也不是无限历史：重写会压缩过去的命令，不能把它当作长期审计日志。

例如业务允许最多五分钟数据损失，首先要从业务角度定义“哪些数据可丢、哪些不可丢”。缓存条目通常可重建；验证码或临时会话丢失可能导致用户重新操作；订单支付状态通常不能仅依靠 Redis 恢复。不同数据可以放在不同实例或采用不同的权威存储，避免一个持久化设置承担互相矛盾的要求。

### 最小故障演练

在隔离实例写入一组测试键，记录时间和数量；等待一次成功快照，继续写入第二组；按演练方案停止实例并恢复。比较恢复后两组键，观察与预期丢失窗口是否一致。对 AOF 另行验证不同刷盘设置下的启动结果。演练不能在生产实例直接使用 FLUSHALL、删除 AOF 文件或强制关机。

关注 INFO persistence 中的 rdb_last_bgsave_status、aof_last_bgrewrite_status 等状态，结合磁盘剩余空间和后台任务耗时判断。持久化失败后，实例可能继续响应读写，但预期恢复能力已经下降，应及时告警。若同时启用 RDB 与 AOF，重启时通常优先使用 AOF 恢复较完整的数据；实际操作仍按当前 Redis 版本文档和备份流程执行。

### 选择时不要只看性能表格

“RDB 文件一定比 AOF 小”“AOF 恢复一定慢”只是常见趋势，不是所有数据集和版本的固定规律。应该用实际数据量测试保存耗时、fork 延迟、重启恢复时间与峰值内存。尤其在共享小内存服务器上，后台子进程与写时复制可能带来明显的资源波动。
