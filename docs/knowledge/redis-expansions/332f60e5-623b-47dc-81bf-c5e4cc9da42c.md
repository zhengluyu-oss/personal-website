## 二十七、Cache Aside 的读写闭环

旁路缓存不只是“查不到就回源”。它还要回答：数据库更新后，旧缓存何时失效？一个常见方案是读请求先查缓存，未命中时查询数据库并写入带 TTL 的缓存；写请求先提交权威数据库，再删除相关缓存键。删除失败须记录并重试，否则旧值可能一直留到 TTL 结束。

    读：GET 缓存 → 未命中 → 查数据库 → SET 缓存 EX 300
    写：更新数据库成功 → DEL 对应缓存

这种流程仍有并发窗口。比如读请求先查到旧数据库值，写请求更新并删缓存，随后读请求又把旧值写回缓存。TTL 能限制最长陈旧时间，版本号、延迟二次删除或更严格的协调机制可按业务一致性要求选择。不要把“先删缓存再更新数据库”当作无条件正确的固定公式。

### 三类问题如何区分

| 问题 | 触发条件 | 首要措施 |
| --- | --- | --- |
| 穿透 | 不存在的 ID 持续回源 | 参数校验、短 TTL 空值、布隆过滤器 |
| 击穿 | 单个热点 key 失效，大量请求同时回源 | 单飞加载、互斥重建、热点预热 |
| 雪崩 | 大量 key 同时失效或 Redis 整体不可用 | TTL 抖动、容量规划、限流和降级 |

缓存空值应使用明确的“未找到”标记，而非和合法空结果混淆；TTL 通常短于正常缓存。布隆过滤器可能把不存在的值判断为“可能存在”，因此不能取代数据库核验，而且新增数据时要同步维护。互斥重建要有超时、失败释放与兜底，不能让所有请求无限等待。

### 可观测性与演练

监控命中率、回源 QPS、数据库连接池、缓存加载耗时、过期与淘汰计数，以及热点 key。命中率高也可能掩盖少数热点 key 的过大负载。可在隔离环境演练 Redis 超时、热点 key 过期、数据库变慢和批量过期，确认限流或降级策略真正生效。

缓存是性能层，不应成为权限判断的唯一来源。用户权限撤销、价格变更或库存扣减等业务，要先定义允许多长时间的旧值，再决定是否适合缓存与如何失效。

## 二十八、把一致性要求写成可验收的数字

“缓存要一致”过于模糊。商品介绍允许五分钟旧值，订单支付状态可能要求提交后立即可见，权限撤销则需要尽快生效。先列出每类字段的可接受陈旧时间、错误返回和缓存故障时的降级规则，再决定 TTL 与失效策略。对高风险数据，直接查询权威存储可能比设计复杂缓存更合适。

缓存删除失败不是小事：如果旧值仍在 Redis，用户会继续看到错误数据。应用应在日志与指标中记录失败、请求 ID 和目标 key 的非敏感摘要，并有可重试的补偿流程。重复删除同一个缓存键通常可安全执行，但补偿流程也应有次数和告警界限。

### 一个热点 key 的时间线

假设 product:1001 的缓存于 12:00 到期。12:00:00 有 500 个请求同时 GET 未命中，若全部查 MySQL，就形成击穿。单飞加载让一个请求负责回源，其他请求等待短时间或使用允许的旧值。负责加载的请求失败时，等待者必须超时并得到受控结果；不能无限排队。互斥锁的持有时间和数据库查询超时也要匹配。

### 雪崩不只有同一 TTL

Redis 实例故障、网络中断和连接池耗尽，同样会导致大量缓存不可用。TTL 抖动只能缓解同时过期，不能解决服务整体故障。系统需要回源限流、数据库连接保护、降级页面或明确错误，并演练恢复后的缓存重建速度。

布隆过滤器适合大规模存在性预检，但可能误判为“可能存在”；仍需实际查询。它还需处理新增数据与重建版本。缓存空值简单但要防止空值长期掩盖刚创建的记录，因此通常使用较短 TTL 或写入时主动失效。
