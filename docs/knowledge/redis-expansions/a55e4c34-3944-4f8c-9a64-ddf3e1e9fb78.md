## 五、一次请求怎样经过 Redis？

把 Redis 放在应用旁边，不等于每次请求都会更快。一次命中仍经历 key 序列化、网络往返、Redis 查找和值反序列化。它省下的应当是更昂贵的数据库查询、计算或跨服务调用。先测量原请求耗时、缓存命中率和新增的 Redis 往返，再决定是否缓存。

Redis 将键和值主要保存在内存，但持久化文件、复制缓冲区和客户端连接仍会消耗磁盘与内存。内存访问、高效数据结构和较短的命令执行路径，让常见操作延迟较低；“Redis 整个程序只有一个线程”并不准确。网络 I/O、持久化等工作可以由其他线程或子进程参与。复杂命令、巨大的值和拥塞网络仍会让请求变慢。

### 一个最小缓存示例

    SET product:detail:1001 '{"name":"键盘","price":199}' EX 300
    GET product:detail:1001
    TTL product:detail:1001

EX 300 表示五分钟后过期。TTL 返回 -1 表示键存在但未设置过期时间，-2 表示键不存在。示例 JSON 只是字符串，Redis 不会自动理解其中的价格字段。价格等权威业务数据仍由数据库维护，缓存保存可重建的副本。

### 场景与边界

| 需求 | 可选结构 | 还需要考虑 |
| --- | --- | --- |
| 热点详情 | String 或 Hash | 写入后失效或更新缓存 |
| 短时验证码 | 带 TTL 的 String | 尝试次数限制与重复提交 |
| 计数 | String 加 INCR | 是否要落库、是否允许重复 |
| 排行榜 | Sorted Set | 同分排序和分数计算规则 |
| 临时互斥 | 带 TTL 的键 | 唯一持有者、安全释放 |

跨多表约束、复杂查询、审计和不可丢失的核心记录，通常仍由权威数据库承担。缓存失效时，要明确系统是回源、限流、降级还是拒绝，不能让每个请求同时压向数据库。

### Key 设计与排查起点

使用稳定的业务前缀，如 product:detail:1001。避免把手机号或访问令牌明文放进 key 名，它们可能出现在排查工具和监控中。缓存键设置合理 TTL；同批创建的键可加入少量随机过期抖动。分别观察大 key、热 key、命中率、内存和慢命令。一个很大的 Hash 或 List 即使只有一个 key，也可能成为瓶颈。

## 六、把“快”拆成可测量指标

性能讨论至少区分平均延迟、P95/P99 延迟、吞吐量和端到端响应时间。一个 Redis 命令耗时低，不代表用户看到的页面快：应用线程等待、序列化、网络距离、数据库回源和浏览器渲染都在路径上。先从业务接口记录缓存命中与未命中的耗时分布，再决定优化哪个环节。

Redis 核心命令执行会被耗时命令占用。对庞大集合一次取出所有成员、在生产运行 KEYS *、大范围删除或传输大值，都可能影响同实例其他请求。命令的时间复杂度要结合数据规模看；单次命令“能运行”不意味着适合高并发线上路径。排查时可结合 SLOWLOG、INFO commandstats 与客户端超时日志，但要保护日志中的敏感值。

### 缓存命中与失效示意

某商品接口每秒 1000 次请求，缓存命中率为 95%，仍有约每秒 50 次回源。若热点键恰好同时过期，短时间内回源量可能远高于这个平均数。将 Redis 放入架构时，要让数据库能承受合理的未命中峰值，或设置限流和单飞重建，而不是只看平时命中率。

### Redis 不能替你定义数据所有权

先问“这份数据的最终正确版本在哪里”。如果在 MySQL，Redis 是副本，必须制定失效和重建规则。如果 Redis 是唯一写入位置，则持久化、备份和故障恢复成为核心设计。混淆这两种角色，是很多缓存与数据丢失问题的根源。

学习时可先用一个小实例运行 PING、SET、GET、TTL、DEL，并观察每条命令的返回，再模拟过期与服务不可用。这样的练习能把 Key-Value 模型与业务故障处理联系起来。
