# 日记多轮对话上线与回滚

本功能把“问日记”和“做复盘”首轮及追问绑定为私密对话。它在已有 PostgreSQL 数据库中增加 `diary_conversation` schema；不修改原日记、`diary_ai` 九张表或原有单次问答接口。每轮仍由原队列处理，单独计入模型用量。

## 上线顺序

1. 在生产 PostgreSQL 对日记数据库做可恢复备份，并在隔离库验证恢复。核对备份文件留存位置、可用空间和恢复权限。
2. 以现有日记迁移角色运行 `scripts/diary/005-diary-conversations.sql`。它应在 `002-private-diary-ai.sql` 之后执行，可重复执行；应用运行角色只有私密表的必要权限，RLS 始终开启。
3. 验证新 schema 版本为 1、两张业务表均启用并强制 RLS，原 `diary_ai` 收据和九表检查仍通过。
4. 发布后端，先验证旧 `/diary/auth/ai/questions`、`/reviews`、`/reports` 和日记保存不受影响；再发布前端。新界面以连续对话为主，旧单次报告保留在折叠入口。
5. 使用站主账号在低额预算下分别完成“问日记”三轮及“做复盘”首轮加两次追问，刷新页面核对问题、回答、引用和状态。记录每轮用量。测试取消、未知结果、引用失效与手机宽度布局；使用只读账号验证对话 API 为 403，匿名访问为 401。

测试环境已在隔离 PostgreSQL 中重复执行迁移，并完成备份恢复：恢复库保留对话与轮次数据及强制 RLS。真实模型小额验收和生产备份、迁移、发布须在生产操作时完成，不能由受控模型测试代替。

## 回滚

先停止展示新对话入口并回滚前端，再回滚后端。原单次接口和报告继续可用；保留 `diary_conversation` schema 与数据，不执行删除。排查失败任务时仅查看任务 ID、状态和脱敏日志；不导出日记正文或模型输入。若要恢复此前数据库状态，只从已验证的备份执行，并先评估备份之后新增的日记与报告，避免覆盖正常写入。
