## 项目定位与展示目标

这个项目是 AI 搜索相关产品的对外展示入口，用来解释产品定位、组织能力介绍，并引导访问者进入登录页面。它的职责是帮助首次访问者建立理解，而不是在落地页中直接执行搜索任务或生成分析报告。

我参与这一展示页的前端实现，使用已有 React 与 TypeScript 技术栈，将导航、首屏、能力介绍、选择理由、案例和联系区域组织成连续的浏览路径。这里展示的是页面开发与信息组织工作，不将静态展示的产品能力误写成已经在该页面实现的后台能力。

## 我承担的工作与页面拆解

### 首屏：先说明定位，再提供明确入口

首屏集中展示产品名称、主要介绍和操作按钮。标题承担快速传达产品方向的职责，补充说明提供更多上下文，登录及开始使用入口连接登录路由。信息层级要让访问者先理解产品，再决定是否进入系统，而不是一开始就堆满功能说明。

我关注文案与组件结构的对应：主标题、说明文字和入口各自有不同视觉权重，按钮不能与普通文本混在一起。对于代码中没有实际行为的展示按钮，不将它写成已完成的业务交互，也不把点击效果等同于整个用户转化流程已经落地。

### 固定导航：连接同页不同内容区域

导航围绕功能、选择理由、案例和联系等区域设置页内锚点，并提供独立的登录入口。页内跳转和进入登录页面是两类不同动作，前者用于浏览介绍，后者才离开当前展示页。

我参与这些区块与导航关系的实现，让区域标识和跳转目标匹配，保证内容扩展后依然可以从导航到达对应部分。对于较长展示页，清楚的章节入口比单纯增加动画更能帮助访问者找到关心的内容。

### 能力介绍：将抽象概念拆成可浏览的模块

能力区用多个模块介绍产品方向，包括多平台数据、地域相关信息、监测与报告等主题。这些模块承担说明作用，通过标题、辅助说明和视觉标识建立层级，让访问者可以逐项浏览，而不是阅读一整段难以区分重点的介绍。

我在这部分的工作是将展示内容映射到可维护的页面模块，保持同类内容的结构一致，并与后续选择理由、案例和联系信息形成顺序。介绍的是产品希望解决什么问题，不能据此推导出每一个后台模块都是我负责开发的。

## 技术实现与范围边界

### 宽窄屏阅读与基础访问体验

桌面端以并列模块展示能力，窄屏时按内容顺序排列。标题字号、按钮区域和模块间距也要随可用宽度调整，不能只是把桌面页面等比例缩小。我参与响应式布局与展示细节，让首屏说明、导航和下方内容在不同宽度下仍能被顺序阅读。

页面采用 React 组件组织区块，TypeScript 为组件与数据提供类型约束，路由入口使用项目已有机制。样式和布局沿用仓库内的前端方案，不为单个展示页另建一套应用架构。

技术重点包括区块结构、锚点关联、入口路由和内容层级。与数据处理平台相比，这个项目的复杂度主要在对外信息组织，而不在队列、结算或后台任务编排；我保留这种差异，不为了让介绍显得更复杂而增加代码中未实现的功能。

## 配套业务系统：从产品介绍到分析工作台

展示页背后还有面向使用者的 GEO 分析工作台。它与展示入口属于同一产品背景，但承担不同职责：展示页帮助理解产品，工作台围绕项目、关键词、AI 对话、品牌表现、引用来源和分析报告组织实际数据。以下按实际代码说明这条业务链，不将所有模块的存在等同于由我独立设计和交付整个系统。

### 项目与关键词：确定分析范围

工作台首先确定当前项目，再维护主题与 AI 问题关键词。关键词具有启用与停用状态，查询和报告选择需要尊重这个状态，避免后台已经关闭的问题仍被当作有效范围。

全局搜索同时匹配主题名称与关键词文字，并整理成去重后的关键词标识。用户已有的关键词筛选再与搜索结果取交集，而不是一方直接覆盖另一方。这里特别区分三种含义：没有设置限制、主动选择空集合、搜索后没有匹配项。最后一种情况不能回退成查询全部数据，否则用户搜索不到内容时反而会看到与输入无关的统计。

### 对话详情：把回答正文与信源连接起来

对话详情不仅展示 AI 回答，还连接来源列表、截图预览和前后记录导航。不同平台的回答格式并不一致，可能包含转义换行、思考区标记、内部媒体块标记和不同形式的引用序号。

展示前先整理换行和不应直接展示的标记，再按已有格式分开思考部分与正式回答，最后将不同平台的引用标记转换为指向信源的统一链接。零基与一基序号需要明确转换，多个相邻引用也要保持可读的分隔，避免点击正文中的引用后跳到错误来源。

这类数据适配直接影响使用者是否能核对一段回答的依据。页面显示完整并不只是文字全部渲染出来，还包括回答、引用序号和来源列表之间有可以追查的对应关系。

### 引用来源：从汇总分布下钻到文章

引用来源分析按平台组织统计，同时保留文章标题、链接、引用次数、相关 AI 平台和发布时间等明细。使用者既可以查看来源平台分布，也可以进一步判断某篇文章被哪些平台引用。

导出不是简单截取当前可见表格。数据整理层明确输出字段和平台名称，将日期格式化，并保留来源与引用关系；平台分布导出还按品牌生成占比列。大量数据导出时提供已完成比例和预计剩余时间，完成前不提前显示为百分之百；记录较多时提示缩小日期范围，让使用者理解导出范围与等待成本。

### 报告生成：区分发起请求与报告完成

报告列表按项目和类型查询，生成时可以选择平台与问题关键词。界面在发起成功后回到第一页并刷新相应查询，避免新报告已经创建，用户却仍停留在旧分页而误以为操作失效。列表分别显示生成中、完成和失败状态，完成后再提供报告详情入口。

服务端先核对项目归属、编辑权限和报告数量额度，再创建生成中的报告记录，并将任务交给后续处理队列。主账号与子账号访问同一项目资料时，还需要按真实归属解释报告列表，而不是把当前登录人的编号直接当作所有内容的所有者。

代码中保留了一些尚未启用的重复生成检查分支，因此本介绍不把它们写成已经生效的保证。接口返回报告编号，只代表请求已进入业务流程，并不等于报告已生成，更不代表所有外部数据来源已经成功返回。

## 技术联系与实现关注点

### 从产品入口进入实际分析的一条路径

第一次访问的用户先在展示页理解产品能解决什么问题，再通过真实登录入口进入工作台。工作台以项目作为查询范围：选择项目后确定当前启用的主题和关键词，再进入 AI 对话、引用来源或报告列表。展示页负责讲清能力与入口，工作台负责实际查询和分析；两者使用不同的组件与路由，不应因为产品名称相同，就把落地页的静态区块当作后台数据界面。

用户在工作台搜索一个词时，匹配条件可能落在主题名称，也可能落在问题关键词。搜索结果与用户已选关键词共同决定最终查询范围；没有设置限制与明确选择空集合是不同语义。若搜索得到空结果，后续统计和列表应保持为空，不能误将空筛选解释为“查询全部”。这类边界直接影响用户是否信任品牌表现和引用来源的统计结果。

打开单条 AI 对话后，回答正文要和引用来源对应。前端整理换行、平台特有标记、思考区和引用序号，再将正文中的引用跳转到来源列表。核查时不是只看回答是否排版整齐，还要检查第一个引用是否真的对应第一条来源、相邻引用能否分别点击，以及截图预览与当前记录是否一致。导出引用来源时，标题、链接、引用次数、平台与时间字段也要保持同一口径。

用户最后生成报告，页面立即显示“生成中”并刷新列表；只有生成完成才进入详情。服务端在创建前检查项目权限、归属与额度，创建记录后再投递后续任务。队列投递和报告完成属于两个阶段，接口返回编号不等于最终内容已经可读。上述工作台机制提供产品背景；在个人职责上，我确认参与的是展示页和已核实的前端信息组织，不把全部分析与报告模块署为个人独立成果。

产品展示入口和分析工作台使用 React 与 TypeScript，但分别按各自应用的路由、组件与接口组织。工作台可见 React Query 的服务端状态管理、Node.js 业务服务、数据库访问分层及 Redis 任务投递；不能把展示页的路由跳转误写为整个数据分析系统都已完成。

这些模块中值得突出的是业务语义一致性：关键词筛选影响哪些记录，引用序号如何落到具体来源，报告由谁访问，以及“生成中”与“已完成”如何区分。对个人经历而言，页面和接口联调的价值也在这些连接处，而不仅是图表或列表的外观。

## 项目实践沉淀

展示类页面同样需要区分内容表达和真实交互：锚点是否匹配、按钮是否有实际目标、能力说明是否准确，都会影响访问者对产品的理解。我的工作重点是把抽象产品介绍整理成可浏览、可维护的前端页面，而不是通过未经证实的客户数量、可用率或转化率来包装成果。
