## 项目背景与业务目标

内容验收面对的是一条跨平台、跨人员的工作链：先按项目收集内容线索，再补充链接与基础信息，执行点检或分析，最后把可核对的结果交给业务人员。不同平台的搜索方式、筛选条件和账号状态不相同，单独做一个查询页面并不能完成交付。

我参与的工作覆盖 Vue 管理端、Java 后端、Python 消费者和媒体登录助手。它们作为同一个项目协作：管理端负责把需求表达成任务，后端负责记录和推进任务，消费者执行具体能力，登录助手维护执行所需的账号环境。项目重点是把这些环节串成可查看、可追踪、可处理异常的业务流程，而不只是堆叠采集功能。

## 我承担的工作与功能拆解

### 链接导入：从原始输入追踪到处理明细

验收的输入不只有关键词，也包含单条链接和批量文件。我参与链接导入、任务查询与失败明细的功能衔接，将一次导入保留为可再次查看的任务，而不是上传完后只显示一个临时提示。

任务详情展示任务编号、状态、总数、成功数和失败数，操作者可以从导入列表继续定位某次处理结果。部分记录成功时，失败记录仍需保留对应输入和原因，方便判断应补充资料还是重新处理；任务仍在执行时，也不能因为暂时没有失败就提前视为完成。

这条输入链路与后续搜索点检互补：已有内容可以从链接进入，没有明确链接时则按关键词发现内容。两种入口最后都需要让业务人员回到具体记录检查，而不是只保留一组汇总数量。

### 管理端：把业务需求变成明确的任务参数

我围绕关键词点检的创建和详情页面参与表单、交互与接口联调。创建任务需要关联项目，输入关键词，并选择平台及搜索类型。关键词支持换行、逗号和顿号等输入形式，整理后再提交，避免把一大段文本当成单个关键词。

平台选择不是一个简单下拉框：微信公众号文章、视频号、抖音、小红书、快手对应的搜索项和筛选条件有所区别。界面按平台保存筛选草稿，切换平台时不把刚填写的排序、时间、时长或内容类型等配置混在一起。每个关键词的目标数量、是否补充基础信息、是否转换视频号短链、是否执行标题分析也分别表达，业务人员可以看清这次任务实际会做哪些工作。

标题分析还涉及规则及版本选择。我在展示和对接中把“启用分析”和“选择分析规则”关联起来，而不是把所有输入项始终展开。这样任务创建时能形成明确的执行范围，后续结果也有对应的规则上下文。

### Java 后端：把一次任务拆成可推进的执行步骤

后端不直接在创建请求里执行全部耗时操作，而是保存任务、任务项和步骤。关键词任务创建时先检查项目、关键词、目标数量、平台配置和执行计划，再按平台与搜索类型构造搜索步骤。

总目标数量按“关键词数 × 平台搜索项数 × 每词目标数”确定。这个分母在创建时固定，后续结果回写不随意改变目标，避免执行过程中的进度看似完成、实际却缩小了验收范围。真实链接返回后再进入后续处理，而不是把一个搜索占位项直接当成最终内容成果。

我关注前后端参数与执行计划的一致性：用户关闭标题分析时，关联的规则参数也需要清理；启用基础信息或短链转换时，后端计划要与页面开关对应。平台筛选参数先按平台校验和标准化，再进入步骤参数，降低“表单提交成功但消费者无法理解”的联调成本。

### Python 消费者：承接耗时工作并回传执行结果

消费者从任务流读取消息，把平台搜索等能力交给具体处理器执行。入口对消息内容做类型和必填检查，并通过统一的执行保护与流消费封装衔接工作者标识、阻塞读取、重试次数及积压处理方式。

这一端的工作不是再复制一套后台，而是把“怎么执行”与“业务任务处于什么状态”分开。Java 侧持有任务和步骤记录，Python 侧围绕具体能力执行并回写结果；出现执行失败时，需要让业务侧知道失败发生在哪个环节，而不是只看到一个永远转圈的页面。

在分批搜索的流程中，后端存在继续执行与检查点保存的处理：阶段结果可以先形成链接记录，再带着后续参数推进。这样的组织方式便于对较长任务观察阶段进展，也使前端能够区分“已经找到内容”和“内容后续处理完成”。

### 任务详情：将搜索、处理与分析进度分开说明

我参与把任务详情做成可用于实际验收的工作界面。页面分别显示链接处理和标题分析进展，包含总量、已处理、失败、跳过等状态；正向、负向和未分类结果也分别展示。未分类并不直接等于负向，分析未完成也不应被显示成全部合格。

详情页支持按平台和标题分析结果筛选。任务运行时定时刷新，离开页面后清理计时器，避免页面已经切换却继续发起查询。需要重新分析时，可以明确选择规则发起分析，而不是通过刷新整页暗中触发耗时操作。

导出提供全部结果、当前筛选结果、正向结果和负向结果等口径。这里的重点是让筛选与交付范围对应：页面上看的是什么、导出文件包含什么，需要有明确差别，不能用一个含义模糊的导出按钮让使用者猜测。

### 媒体登录助手：把账号维护纳入同一条链路

桌面端登录助手是执行环境的配套工具，和验收平台一起呈现。账号列表支持按平台、状态、占用情况和关键词筛选，分页查看；操作包含重新登录、环境重新绑定、调试入口，以及批量下线、解绑或删除等维护能力。

我关注账号状态与操作反馈的联动。筛选变化后回到合适的列表页，重新登录按当前账号归属约束进入相应流程，操作结束刷新列表状态；异常反馈让维护人员知道操作是否真正完成。界面区分空闲与被占用的账号，避免把“列表里存在”误当成“当前可以立即执行任务”。

这部分公开展示只描述账号维护与协作流程，不公开真实账号、会话数据、网络配置和内部资源信息。

## 技术组织与协作方式

### 配套工具：直播录屏评论识别与截图归档

在验收资料整理场景中，除了通过链接执行在线任务，也会遇到只有直播录屏、需要从视频中找出评论画面的情况。这里使用独立的 Python 离线处理工具，输入是录制好的视频，不依赖管理端页面保持打开，也不把视频处理伪装成 Java 任务消费者中的同一个步骤。

这部分将工作拆成取帧、OCR、评论解析和归档几个阶段。第一阶段围绕评论区域抽取画面，结合滚动状态和覆盖关系选择候选帧，减少相邻画面中重复内容带来的后续处理。平台和评论区域布局使用配置表达，避免把某一份录屏的尺寸直接当作所有平台的固定规则。

第二阶段先识别文字与位置，再处理用户名、评论正文及界面标记之间的关系。等级标记、边界截断和不完整文字会影响识别，流程中为这些情况保留补救与解析环节。OCR 的文本行并不直接等于最终用户清单，需要继续完成身份归并与评论记录整理。

归档按片段产生结果，再跨片段形成场次级输出。现有入口区分全部用户、指定用户、内部名单、目标覆盖和脚本名单等输出口径，共用底层身份处理，而不是每个输出方式重新执行一遍所有识别过程。业务上可以围绕特定名单检查资料覆盖情况，也可以按用户查找对应的评论画面。

我在这类资料整理工作中关注输入、阶段结果和交付口径的对应：记录实际处理的是哪些片段，区别识别到的文字、归并后的用户与最终可用截图；不能直接把帧数、评论条数或用户数当成同一个指标。页面和项目介绍也据此区分处理流程，而不以未核实的识别准确率或处理速度包装成果。

### 阶段复用、重跑与结果核查

离线任务可能耗时较长，重新整理目标名单不意味着必须重新识别所有视频。实现中将解析核心与不同归档模式分开，并依据输入来源、有效配置和结果指纹判断是否能够复用。归档前读取当前有效的解析结果，而不是随意选取某个旧输出目录。

阶段准备与解析核心使用文件锁保护，避免两个操作同时写入同一结果；复用前检查产物完整性和关联信息，不能因为目录存在就视为任务完成。每个阶段保留摘要与异常信息，便于区分 OCR 资料不完整、解析降级和归档范围不足。

工具另有模拟测试素材的生成能力。模拟内容与真实录屏识别结果应分别标识和核查，不能把测试样例称为真实用户发言。本项目公开展示的是阶段编排、资料组织和核查思路，不公开原始录屏、客户名单或真实评论内容。

| 部分 | 承担的职责 | 与其他部分的连接 |
| --- | --- | --- |
| Vue 管理端 | 创建任务、配置筛选、查看进度、筛选导出 | 调用业务接口，展示任务与结果状态 |
| Java 业务后端 | 参数校验、任务建模、步骤编排、结果持久化 | 将业务请求转换为可执行计划，接收结果 |
| Python 消费者 | 执行搜索等耗时能力、处理阶段结果 | 消费任务消息，回传结果与失败信息 |
| 桌面登录助手 | 账号筛选、登录维护、占用状态管理 | 为执行环节提供可维护的账号环境 |

我在这条链路中的工作不只集中在页面样式。前端字段是否有对应后端语义、任务状态是否能够被消费者正确推进、结果能否被业务人员复核，都是联调中需要一起处理的问题。实现上沿用各端已有的组件、接口和任务机制，避免为某一个平台增加一套彼此割裂的业务流程。

## 实现中重点处理的问题

### 一次关键词验收任务如何落地

以业务人员要核对某个主题在多个平台上的内容为例，入口先确定项目、关键词、平台和各平台搜索类型，再决定每个组合要取得多少条内容。管理端把换行、逗号等输入方式整理成关键词列表，同时保存每个平台独立的筛选条件；切换到另一个平台后，刚设置的时间范围和排序不会被误用于新平台。操作者还可以选择是否补齐基础信息、是否进行标题分析，以及分析所用的规则。这些选择最终要组成后端能够解释的任务计划，而不是只停留在前端表单。

任务创建后，Java 服务把关键词与平台搜索项展开成步骤，并固定本次运营目标。Python 执行端处理搜索工作并回传阶段结果。详情页分别汇报内容获取与标题分析的进度：目标尚未达到可能是仍在搜索、平台已无更多结果，也可能是某一步失败；已经拿到链接也不代表基础信息和分析全部完成。我参与前后端字段与这些阶段状态的联调，让业务人员能沿“任务—步骤—结果记录”找到问题发生的位置。

到交付时，页面可以按关键词、平台和分析结果缩小范围。全部导出、当前筛选导出与正负向结果导出分别代表不同口径；在点击前先把范围说明清楚，避免屏幕上看到的是某个平台的数据，交付文件却混入其他平台。人工复核也可沿记录返回原始链接，不依赖一串脱离上下文的汇总数字。

### 账号异常和离线资料怎样进入核查

任务执行依赖可用的媒体账号。登录助手中的账号存在、登录有效和当前空闲是三件事：维护人员先按平台、状态、占用情况定位账号，再根据状态决定重新登录、重新绑定环境或下线。操作后刷新列表，使后台任务遇到执行异常时，能够回到账号准备环节排查，而不只在验收页面反复重试。

如果输入不是可直接查询的链接，而是一段直播录屏，离线处理链路先依据画面中的评论区域挑选候选帧，再识别文字、归并用户和评论，最后按场次与名单口径归档截图。原始帧、OCR 行、识别出的用户、最终可交付截图各有不同数量；需要补跑时先核对现有阶段产物和指纹，再决定复用解析结果还是重做识别。这里的截图归档属于配套 Python 工具，不与 Java 关键词任务混写为同一执行步骤。

- **平台差异**：搜索类型和筛选参数按平台组织，不假设所有平台都有相同能力。
- **目标与进度口径**：创建时固定验收目标，将结果数量、处理数量和分析数量分开，避免一个百分比掩盖不同阶段。
- **长任务可见性**：任务执行放在消费者侧，管理端持续展示阶段状态，离开页面及时停止刷新。
- **规则与结果对应**：分析开关、规则版本、正负向分类和导出范围互相对应，便于后续核查。
- **运行环境可维护**：将账号登录、状态与占用管理放在配套助手中，而不是让维护人员只依赖后台日志判断。

## 项目实践沉淀

这段工作让我把表单、接口、异步执行和结果页面当成一个整体来设计。一个功能是否完成，不能只看按钮能否点击或接口是否返回成功，还要看业务人员能否确认任务目标、理解当前状态、定位异常，并拿到符合范围的交付结果。公开页面保留业务过程和技术设计，不展示客户内容、内部账号及未经核实的效率数字。
