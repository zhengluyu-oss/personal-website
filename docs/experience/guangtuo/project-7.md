## 项目背景与业务流程

内容生产并不是输入一个关键词、得到一段文字就结束。实际工作还需要观察生成过程、检查评分、复核内容、配置头图，并决定以草稿还是正式内容上传。批量处理时，单篇失败也不能让操作者失去对其他文章状态的了解。

我参与基于 Vue 与 FastAPI 的内容生成和发布工具，将生成过程与文章管理串成一条可操作的流程：配置生成需求，观察阶段进展，查看生成结果与评分，进入人工复核，补充图片，再执行上传。重点是把模型调用转成可管理的业务状态，而不是只做一个对话窗口。

## 我承担的工作与功能拆解

### 生成输入：关联关键词与提示词配置

工具提供单关键词生成入口，并有关键词管理和提示词配置页面。生成前需要把当前输入、所选配置和请求条件对应起来，不能让界面已经修改、执行端却仍使用上一次的设置。我的工作包含生成入口与服务端反馈的衔接，让输入问题、正在处理和生成异常能够在合适的阶段被识别。

提示词是内容生产配置的一部分，模型输出仍需要进入后续检查。公开介绍只说明配置与执行的关系，不展示内部提示词、模型凭据，也不将接入生成服务描述为训练了底层模型。

### 生成过程：让长请求有可读的阶段反馈

生成过程中会经历准备、模型调用、评分、修复和保存等阶段。前端按事件更新当前阶段、轮次、步骤数量和耗时信息，让使用者能够知道系统正在做什么。评分事件还区分机器评分、GEO 评分、是否通过以及修复轮次，不将所有状态压缩成一个没有解释的进度条。

我围绕事件消费和页面状态参与实现：批次进度反映整体处理情况，阶段事件说明当前步骤，单篇完成事件包含文章标题、字数和结果状态，最终事件再给出成功与失败数量。这样批量生成既能观察整体，也能定位某篇内容没有完成的原因。

### 流式通信：处理数据分片、取消与登录异常

前端使用 POST 请求获取事件流，通过 Fetch、ReadableStream 与 TextDecoder 持续读取。网络分片不一定恰好是一条完整事件，因此先缓冲数据，再按事件分隔符解析，避免把半段 JSON 当成完整消息处理。

事件按类型交给批次进度、阶段、评分、单篇完成、错误和结束等回调。用户中断或页面停止当前操作时，通过 AbortController 取消请求，取消错误不会被直接当成业务生成失败提示。

这条请求链没有经过普通接口的统一拦截器，因此流式请求自身处理未登录与访问被拒绝等状态，衔接登录页或访问提示页。技术上需要关注的不只是“能收到字符串”，还包括鉴权失败、流被取消和正常结束各自如何反馈给界面。

### 文章管理：把生成结果变成可处理的内容列表

文章列表支持关键词与状态筛选，并可按创建时间或评分等信息排序。每条记录展示标题、关键词、评分、字数、封面、状态和创建时间，操作者可以从列表判断哪些内容需要进一步处理。

我参与将预览、评分、头图设置和上传等入口与文章状态连接起来。单篇操作适合细看和修订，批量状态调整、批量头图、批量删除及上传则服务于集中处理。选中哪些文章、将要改变什么，以及操作完成后如何更新列表，都需要在交互上保持一致。

### 状态约束：区分待复核、可发布与已处理内容

生成结果并不自动等于可发布内容。项目中将“发布就绪”“需人工复核”等状态与编辑、头图设置和上传前操作关联；内容进入后续状态后，对重复上传或修改采取相应限制。

我关注前后端约束的一致性：前端禁用不适用的按钮，提前解释当前记录为什么不能操作；后端仍按文章状态检查，避免仅凭页面限制决定是否允许执行。批量操作也不能绕过单条记录的状态边界。

### 图片与上传：完成发布前的最后一段流程

头图配置和素材管理服务于文章发布，不作为与正文脱节的附属页面。操作者在文章管理中选择需要的头图，确认正文和状态后进入上传环节。

上传对话框区分草稿与正式发布，并提供试运行选项。试运行和正式上传的含义不同，界面需要让用户明确当前操作是否会形成真实发布结果。这里的工作重点是让生成、复核、图片和上传之间形成有边界的交接，而不是生成结束后直接自动公开内容。

素材侧分别管理头图背景与正文插图。图片校验不仅检查扩展名，还检查文件内容对应的格式特征，避免把改名后的非图片文件当作合法素材。我的联调工作关注素材选择、文章关联和不合规输入的提示，让问题尽量在发布前暴露，而不是等目标内容系统拒绝上传时才发现。

## 技术实现与关键细节

| 环节 | 实现重点 | 对使用者的作用 |
| --- | --- | --- |
| 事件流读取 | 分片缓冲、事件解析、取消控制 | 长任务不是黑盒，可以观察和停止 |
| 批次与单篇状态 | 分别接收阶段、评分、完成事件 | 看见局部失败，不与整批结果混淆 |
| 文章管理 | 筛选、排序、预览和批量操作 | 从生成结果中选择需要处理的内容 |
| 发布前校验 | 页面状态限制与服务端规则对应 | 防止不适用的操作与重复上传 |
| 上传配置 | 草稿、正式发布、试运行明确区分 | 对发布结果有可理解的预期 |

## 实现中重点处理的问题

### 从一次生成请求到可管理的文章

操作者选定关键词与提示词配置并发起生成后，页面要同时跟踪整批任务和每篇文章。流式接口返回的网络分片可能截断一条事件，因此前端先缓冲，再解析完整事件，按批次进度、当前阶段、评分、单篇完成、异常和结束分别更新界面。我参与的是这套反馈与业务状态的对应：界面显示“正在评分”时不能误写成文章已保存，某一篇失败也不能把整批其他结果清空。

中途取消、网络中断和服务端明确报错是不同结果。取消通过请求控制器结束读取，界面不把用户主动停止渲染成生成失败；流式请求单独处理未登录和访问受限状态，因为它不经过普通请求拦截器。任务结束后，操作者能从完成与失败数量回到文章列表，按状态或关键词查看具体记录，而不只能看到一次性弹窗提示。

### 复核、头图与上传的交接

文章进入列表后，还要判断内容是否需要人工复核、评分是否满足流程要求、头图是否已经配置。预览入口同时读取文章详情与预览内容，展示前处理 HTML；批量上传先筛掉当前状态不允许上传的文章，并告诉操作者实际会处理多少篇、跳过多少篇。上传参数明确区分草稿、正式发布和试运行，使用者需要知道这次操作会产生什么结果。

头图与正文插图来自素材管理，选择结果要关联到当前文章。上传前对素材类型做文件内容校验，避免仅凭扩展名接受错误文件。前端负责让限制和反馈可理解，后端仍对文章状态执行校验；因此“按钮可点”只是交互条件，不是发布许可本身。我在联调时关注从生成记录、人工复核、图片配置到上传响应这一整条链，出现失败后仍能回到原文章继续处理。

长任务的交互不能只依靠一个 loading。必须区分等待模型、评分修复、保存失败和人工取消；批量操作也不能只给一个成功提示，需要能回到具体文章继续处理。我的工作因此覆盖事件协议、页面状态、文章列表与发布约束的衔接。

项目中的评分用于内容处理流程，不代表对真实性或传播效果的保证。公开介绍说明评分与复核如何配合，不虚构文章质量、发布量或节省工时的数字，也不暴露模型凭据、内部提示词和内容渠道认证信息。

## 项目实践沉淀

这段工作让我更关注 AI 功能的工程化交付：模型调用只是其中一步，真正可用的工具还要处理等待、取消、失败、复核和发布。将这些过程表达为明确事件与状态，前端才能向使用者说明现在发生了什么、接下来可以做什么。
