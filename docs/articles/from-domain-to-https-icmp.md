前几天，我把这个网站从 HTTP 升级到了 HTTPS。过程中遇到一个很典型的现象：域名能解析、服务器能访问、证书也已经安装，但浏览器打开 HTTPS 仍然超时。最后发现，问题不在证书，而在云服务器的 443 端口没有对公网放行。

这件事恰好把几个容易混在一起的概念串了起来：域名、DNS、HTTP、HTTPS、TLS，以及常被拿来测试网络的 ICMP。它们各司其职。理解这条访问链，比死记几个配置命令更有用。

## 先看全程：输入网址后发生了什么

以访问 `https://www.zhengluyu.com/experience` 为例，可以把过程简化为：

```text
输入网址
  ↓
DNS 把 www.zhengluyu.com 解析成服务器的 IP 地址
  ↓
客户端连接服务器的 443 端口
  ↓
TLS 握手：核对证书、协商加密参数
  ↓
浏览器通过加密连接发送 HTTP 请求
  ↓
Nginx 返回页面，或把 /api/ 请求转发给后端
```

这条链上任何一环出问题，浏览器都可能表现为“网站打不开”，但排查方法完全不同。**域名解析成功，不等于端口开放；端口开放，不等于证书正确；`ping` 有回应，也不等于 HTTPS 能用。**

## 域名是什么？DNS 又在做什么？

服务器在网络上有 IP 地址，域名则是便于人记忆和管理的名字。`zhengluyu.com` 是根域名，`www.zhengluyu.com` 是它的一个子域名。浏览器需要先找到域名对应的网络地址，才能向服务器发起连接；这个查询过程由 DNS 完成。

常见的 **A 记录**把域名指向一个 IPv4 地址。例如在域名解析平台分别为 `@` 和 `www` 添加 A 记录，就可以让根域名和 `www` 子域名都指向同一台服务器。`@` 通常表示域名本身，而不是一个叫 `@` 的真实子域名。腾讯云轻量应用服务器的域名解析界面也支持这样添加 A 记录。[腾讯云：添加域名解析](https://cloud.tencent.com/document/product/1207/81333)

需要区分两件事：**注册域名**是取得这个名字的使用权；**配置 DNS 解析**是告诉访问者这个名字应指向哪里。更改解析记录后，也可能因缓存而不是所有地方立即看到新结果。域名本身不会安装证书，也不会自动开放服务器端口。[RFC 1034：域名系统的概念与设施](https://www.rfc-editor.org/rfc/rfc1034)

## HTTP 和 HTTPS：内容相似，传输方式不同

HTTP 是浏览器和网站交换请求、响应的应用层协议。浏览器请求一篇文章，服务器返回页面和数据，靠的就是 HTTP 的语义。没有 TLS 保护的普通 HTTP 通常使用 80 端口；在传输链路上，内容可能被读取或篡改。

HTTPS 可以理解为**在受 TLS 保护的连接上使用 HTTP**，通常使用 443 端口。TLS 为通信提供加密、完整性保护，并让浏览器核对服务器证书是否匹配正在访问的域名。它保护的是传输过程，不意味着网站代码一定没有漏洞，也不会让域名和访问目标完全隐身。[RFC 9110：HTTP 与 HTTPS URI 语义](https://www.rfc-editor.org/rfc/rfc9110.html#section-4.2)

证书不一定需要购买。本站使用 Let’s Encrypt 提供的免费证书，并设置了自动续期。证书签发之后，还要让 Nginx 正确加载证书、监听 443，并保证云平台防火墙允许公网访问 443；少了任何一步，外部用户都可能打不开 HTTPS。[Let’s Encrypt 官方网站](https://letsencrypt.org/)

> 一个容易忽略的细节：现代网站也可能使用基于 QUIC 的 HTTP/3。这里讲的“HTTPS 连接 443/TCP”指本站当前使用的常见 Nginx/TLS 部署，不是说所有 HTTPS 流量永远只走 TCP。

## 80 和 443 是什么？为什么放行一个还不够？

**IP 地址负责找到一台机器，端口负责找到这台机器上提供某种服务的入口。**同一台服务器可以同时运行网站、数据库、远程登录等服务，它们不能只靠同一个 IP 区分。TCP 和 UDP 的端口号范围是 0～65535；这里讨论的 80 和 443 是网站常用的端口约定，不是固定写死、不可更改的“魔法数字”。

- **80/TCP** 通常接收普通 HTTP 请求。用户输入 `http://www.example.com` 且没有写端口时，浏览器默认访问 80。在本站，80 主要负责把用户跳转到 HTTPS，也为证书的 HTTP 域名验证保留入口。
- **443/TCP** 通常接收使用 TLS 的 HTTPS 请求。用户输入 `https://www.example.com` 且没有写端口时，浏览器默认访问 443。本站的 Nginx 在这里加载证书、建立加密连接，再处理页面与 API 请求。
- 端口也可以显式写在网址里，例如 `https://www.example.com:8443`；这时访问的就是 8443，而不是默认的 443。但对公众网站而言，使用默认端口更方便。

“服务器监听 443”和“腾讯云防火墙允许公网访问 443”是两道独立的检查。前者说明 Nginx 准备接客，后者说明外面的请求能走到门口。**只配置证书、不监听 443，或只监听 443、云防火墙却拦住它，都不能让公网 HTTPS 正常工作。**同理，80 开着只能说明 HTTP 入口可能可用，不能推断 443 也已放行。

浏览器访问网站时，客户端自己也会使用一个临时源端口；这里说的 80/443 指的是**服务器的目标端口**。至于下面的 ICMP，它不使用 TCP/UDP 端口号，因此“放行 ICMP 的 443 端口”本身就是把不同概念混在一起了。

## ICMP 是什么？它和 HTTP、HTTPS 是什么关系？

ICMP 全称是 **Internet Control Message Protocol**，即互联网控制报文协议。它用于在 IP 网络中传递控制和差错信息，例如目标不可达等。日常最熟悉的 `ping`，通常使用 ICMP Echo Request 和 Echo Reply 来观察目标是否回应以及往返耗时。[RFC 792：ICMP](https://www.rfc-editor.org/rfc/rfc792)

ICMP **不是 HTTP 的前置步骤**，HTTPS 也**不依赖先 `ping` 通**。一次正常的网页访问可以完全不发送 `ping`。两者的关系更像不同的检查工具：

- DNS 查询：这个名字能否找到地址？
- ICMP `ping`：目标是否回应这种网络探测？
- TCP 连接：目标端口能否建立连接？
- TLS 握手：证书、域名和加密协商是否正常？
- HTTP 请求：页面或接口是否返回正确内容？

因此，**`ping` 通不代表 443 端口开放；`ping` 不通也不代表网站一定打不开**。有些服务器或网络会限制 ICMP 回应，但照样正常提供 HTTP/HTTPS。排查网页问题时，要测网页本身，而不能只看 `ping`。

## 我这次是如何配置域名与 HTTPS 的

这次实践使用的是腾讯云轻量应用服务器，但思路适用于大多数自建网站。

1. **域名解析。**在域名控制台配置根域名与 `www` 的 A 记录，让它们指向服务器公网 IP。可以用 `nslookup www.example.com` 检查解析结果。
2. **网站服务。**确认 Nginx 已经能在 80 端口提供页面；此时 `http://` 可访问，只说明 HTTP 这一段正常。
3. **申请证书。**通过 Certbot 和 Let’s Encrypt 为要访问的域名申请证书。证书应覆盖实际使用的主机名，例如根域名和 `www`；还要安排自动续期。
4. **配置 HTTPS。**让 Nginx 在 443 端口加载证书并服务页面，先在服务器上检查配置，再从公网验证证书和页面。
5. **放行云防火墙。**在轻量应用服务器实例的“防火墙”页签添加入站规则：TCP 443，来源为需要访问网站的用户范围。面向公众的网站通常允许所有 IPv4 来源。不要误删 80 端口：它还用于 HTTP 跳转和常见的证书域名验证方式。[腾讯云：管理实例防火墙](https://cloud.tencent.com/document/product/1207/44577)
6. **最后再跳转。**确认 HTTPS 已从公网正常访问后，才把 HTTP 请求重定向到 HTTPS。过早跳转会把原本能打开的 HTTP 用户送到一个仍然不可达的地址。

这次真正卡住的是第 5 步：证书已经签发，服务器本机访问 HTTPS 也正常，但公网 443 超时。放行腾讯云轻量服务器的防火墙规则后，公网访问才恢复正常。换句话说，**证书解决“可信且加密”，防火墙解决“能不能连进来”**，二者不能互相替代。

还有一个容易误会的界面状态：腾讯云“域名解析”页里的“HTTPS 未设置”，指的是腾讯云一键设置 HTTPS 的历史记录；如果像本站这样直接在 Nginx 中部署证书，不能仅凭该标记判断网站是否支持 HTTPS。最终应以浏览器实际访问和证书校验为准。[腾讯云：为网站设置 HTTPS](https://cloud.tencent.com/document/product/1207/84359)

## 遇到问题时，按顺序检查

- **域名打不开，IP 可打开：**先检查 DNS 记录是否指向预期服务器，以及解析是否已生效。
- **HTTP 可打开，HTTPS 连接超时：**先检查 Nginx 是否监听 443，再检查云平台防火墙是否允许 TCP 443。
- **HTTPS 能连接，但浏览器提示证书错误：**检查证书是否覆盖当前域名、是否过期，以及 Nginx 加载的是否为正确证书。
- **首页正常，接口失败：**检查 Nginx 的 `/api/` 转发和后端服务，不要把它误判为 DNS 或 ICMP 问题。
- **`ping` 不通，但网页正常：**网站可能限制了 ICMP；以 HTTP/HTTPS 请求结果为准。

命令行里，`nslookup` 适合看解析，`ping` 适合观察 ICMP 回应，而 `curl -I https://www.example.com` 更接近实际网页访问：它会尝试连接、验证证书并读取 HTTP 响应。各工具回答的是不同的问题，不能用一个命令代替整条访问链的检查。

## 写在最后

我现在会把“访问网站”拆成几层来想：**名字找不找得到（DNS）→ 路能不能走（网络/端口）→ 身份和加密是否正确（TLS）→ 内容是否返回（HTTP）**。ICMP 可以帮助观察其中一部分网络状态，但它不负责加载网页，也不是 HTTPS 的开关。

理解这些边界之后，配置域名和证书就不再是一串碰运气的操作。每遇到一个报错，先确定它发生在哪一层，再用对应的工具去验证，通常会比反复重装证书更快找到原因。
