# 从 JWT 登录出发，理解加密算法到底在保护什么

登录后，服务器常会给浏览器一个令牌。以后访问需要身份的接口时，浏览器带上它，服务器就能识别用户。许多人第一次接触 JWT（JSON Web Token）时，会以为“令牌里的用户信息被加密了”。实际上，常见的三段式 JWT 通常是**签名后的 JWS**：它保护内容不被悄悄篡改，却不保证内容保密。沿着一次登录流程，我们可以把编码、哈希、消息认证码、数字签名和加密各自解决的问题讲清楚。

## 一次登录，数据经过了哪里

假设用户输入账号和密码。浏览器通过 HTTPS 把它们发给服务器；服务器用密码验证算法比对数据库中保存的密码摘要；验证通过后，服务器签发一个访问令牌；浏览器在后续请求中携带令牌；服务器验证令牌，再决定能否访问资源。

这条链路至少涉及四个不同目标：传输途中不被旁观者读取、数据库泄漏后尽量保护原密码、令牌不能被伪造或篡改、令牌到期后不能继续使用。没有一种“加密算法”能单独完成所有目标。判断技术方案之前，先问：**要防止谁、在哪个环节、做什么？**

## 先拆开一个 JWT

常见的签名 JWT 写成 `header.payload.signature`。前两段通常是 JSON 分别经过 Base64url 编码；第三段是对前两段进行签名或消息认证得到的结果，再经过 Base64url 编码。示意载荷如下，均为虚构数据：

```json
{"sub":"user-123","iss":"example-app","aud":"example-api","iat":1700000000,"exp":1700003600}
```

`sub` 指主体，`iss` 指签发者，`aud` 指预期接收者，`iat` 是签发时间，`exp` 是过期时间。这些字段不是把权限交给前端决定的授权魔法；服务端仍要验证签名、允许的算法、签发者、接收者、有效期，并结合业务规则判断用户权限。

Base64url 只负责把字节变成适合 URL 和 HTTP 传输的字符。任何拿到令牌的人都能解码前两段，所以不要把密码、身份证号、密钥等敏感信息放入普通签名 JWT。签名后的内容“可读但不可随意改”；若内容本身必须保密，需要另行设计，例如使用 JWE，且不能省略 HTTPS。

## 编码、哈希、加密、签名，不是一回事

| 手段 | 想解决的问题 | 是否需要密钥 | 能否还原原文 | 登录中的例子 |
| --- | --- | --- | --- | --- |
| Base64url 编码 | 便于传输 | 不需要 | 可以直接解码 | JWT 的头部和载荷 |
| 普通哈希（如 SHA-256） | 得到固定长度摘要、检测变化 | 不需要 | 不能从摘要直接还原 | 文件完整性校验；**不宜单独存密码** |
| 密码哈希（如 Argon2id） | 提高猜测密码的成本 | 通常不需要应用加密密钥 | 不能直接还原 | 保存并验证登录密码 |
| HMAC | 让共享密钥双方验证消息来源和完整性 | 双方共享同一密钥 | 它不是加密 | `HS256` 签名 JWT |
| 数字签名 | 由私钥签发、用公钥验证来源和完整性 | 私钥与公钥 | 它不是加密 | `RS256` 等签名 JWT |
| 对称加密（如 AES-GCM） | 保密，并在认证加密模式下检测篡改 | 双方持有相同密钥 | 持密钥者可解密 | 加密需要保密的数据 |
| 非对称加密（如 RSA-OAEP） | 让持有公钥者向私钥持有者传送秘密 | 公钥与私钥 | 私钥持有者可解密 | 加密短小的会话密钥 |

表中“不能还原”不代表绝对安全：攻击者仍可猜候选输入、计算摘要并比对。尤其是人的密码可预测，直接用 SHA-256 即使加盐也通常太快，应选择专门的密码哈希算法。

## 先建立分类：按“目标”和“密钥”看

“加密算法”在日常交流里常被当作密码学技术的统称；严格来说，**加密**主要解决保密性。按密钥关系，加密可分为**对称加密**与**非对称加密**；按安全目标，旁边还有哈希、消息认证码、数字签名、密钥交换与密钥派生等技术。它们可以组合使用，但不能因为都涉及数学运算就互相替代。

| 类别 | 输入与输出 | 主要目标 | 典型技术 | 常见误区 |
| --- | --- | --- | --- | --- |
| 对称加密 | 明文和共享密钥 → 密文 | 保密；AEAD 还提供完整性校验 | AES-GCM、ChaCha20-Poly1305 | 把“加密了”误当作“必然防篡改” |
| 非对称加密 | 明文和公钥 → 密文，私钥解密 | 向特定私钥持有者保密 | RSA-OAEP | 用它直接加密大量文件 |
| 密钥协商 | 各方密钥材料 → 共享秘密 | 建立之后使用的会话密钥 | ECDHE | 把协商误称为“直接加密正文” |
| 哈希 | 任意长度输入 → 固定长度摘要 | 摘要、完整性校验的基础材料 | SHA-256、SHA-3 | 以为摘要一定证明“是谁写的” |
| 密码哈希 | 密码、盐和成本参数 → 验证值 | 增加离线猜密码的成本 | Argon2id、scrypt、bcrypt | 用快速 SHA-256 直接存密码 |
| 消息认证码 | 消息和共享密钥 → 认证标签 | 共享密钥参与者间的来源与完整性验证 | HMAC-SHA-256 | 误以为它能向第三方证明具体是哪一方生成 |
| 数字签名 | 消息和私钥 → 签名；公钥验证 | 验证签发者和完整性 | RSA-PSS、Ed25519 | 把签名说成“私钥加密” |

这里还有一条重要边界：**编码不是密码学保护**。Base64、Hex、URL 编码可以被任何人逆向转换；压缩也不负责保密。反过来，哈希虽然不可逆，却不能把可猜的密码变成无法破解的秘密。

### 对称加密：用同一把密钥保护大量数据

可以把对称加密理解成双方共享一把钥匙：发送者加密，接收者解密。AES 是**分组密码**，一次处理固定大小的数据块；ChaCha20 是**流密码**。它们的原语形式不同，但日常开发更应关注最终使用的**完整方案**，而不是只挑一个响亮的算法名。例如 AES-GCM 是 AES 加上 GCM 工作模式，ChaCha20-Poly1305 则组合流密码与认证器，两者都属于 AEAD（带关联数据的认证加密）。

AEAD 通常给出密文和认证标签。解密前必须验证标签；失败时应拒绝使用明文。它还能把某些无需隐藏、却必须防篡改的字段放入 AAD（关联数据），例如协议版本或业务记录标识。AAD 本身不会被加密。nonce/IV 也通常不是秘密，但必须遵守方案对唯一性和长度的要求；尤其不要在同一密钥下随意重用。不要直接使用仅有保密性而缺少认证的加密模式来“自己拼一个安全协议”。

对称加密适合文件、数据库敏感字段和网络连接中的大块数据。它的难点往往不在运算速度，而在**如何安全地把共享密钥交给正确的人、怎样轮换、泄漏后怎样止损**。

### 非对称加密：公钥与私钥各司其职

非对称加密有一对关联的密钥。公钥可以分发给需要向你发送秘密的人；只有配套私钥的持有者能解密。RSA-OAEP 是一个非对称加密方案，但有输入大小和性能限制，不适合直接拿来加密整本书或大视频。常见做法是**混合加密**：随机生成一个对称密钥，用 AES-GCM 等加密实际内容，再用接收方公钥保护这个对称密钥；接收方先用私钥恢复密钥，再解密内容。具体格式与参数交给成熟协议和密码库处理。

非对称密码体系还有另外两项重要能力，但不是“非对称加密”的同义词：一是私钥签名、公钥验签；二是通过密钥协商建立共享秘密，例如 ECDHE。现代 TLS 通常先完成身份认证和密钥协商，再使用对称的认证加密保护持续传输的数据。这样同时利用了公钥体系的分发优势与对称加密处理大量数据的效率。公钥也不能“拿到就信”：必须确认它确实属于目标身份，否则可能把秘密加密给冒充者。

### 哈希、MAC、签名：证明内容，还是隐藏内容？

普通哈希把输入映射为摘要。它可帮助检查内容是否变化，但若攻击者能同时替换文件和公开摘要，仅有哈希并不能证明来源。HMAC 在哈希之外加入共享密钥，能让不知道密钥的人难以伪造认证结果；因为双方都持有同一把密钥，通常不能向独立第三方证明究竟是哪一方生成消息。数字签名则让签发方独占私钥、验证方只拿公钥，适合多个系统验证同一签发者。

回到 JWT：`HS256` 属于 HMAC，`RS256` 属于数字签名；它们都不是把载荷隐藏起来的加密算法。`SHA-256` 是这些构造可能使用的哈希组件，但**“JWT 用了 SHA-256”并不能说明它的身份验证方式**。要看完整算法、密钥归属以及服务端是否正确验证。

## 密码为什么要“哈希”，而不是“加密”

登录验证并不要求服务器取回用户原密码，只需要检查用户这次输入是否与此前设置的一致。把密码以可解密方式存储，会让数据库和解密密钥共同成为高价值目标。合理做法是为每个密码生成独立的随机盐，使用 Argon2id 这类可调成本的密码哈希算法保存结果；登录时用保存的参数和盐重新计算并验证。盐不必保密，作用是防止相同密码得到相同的存储结果，并削弱预计算攻击。

如果系统已有 bcrypt 或 PBKDF2，也应按现有约束选择合适成本并规划渐进升级，而不是把现存密码机械地再做一次 SHA-256。算法、参数、盐和升级方案应交给成熟库处理，不要自己发明密码存储格式。密码哈希仍防不住弱密码、钓鱼或撞库，登录限速和多因素认证等措施也有价值。

## JWT 的签名如何阻止篡改

以 `HS256` 为例，服务器拿共享密钥对 `Base64url(header) + "." + Base64url(payload)` 计算 HMAC-SHA-256。有人把载荷中的 `role` 改成 `admin` 后，原签名就不匹配；没有密钥，也不能正确生成新签名。注意，HMAC 的安全性依赖高强度、妥善保存的密钥，不能把一句容易猜的口令当生产密钥。

`RS256` 则用私钥签发，公钥验证。把验证能力交给多个服务时，不必把签发私钥发给它们，但仍须可靠分发和轮换公钥。两种方式不是简单的“谁更高级”：单体或受控服务与跨服务验证的密钥管理需求不同，选型应跟随信任边界。

服务器不能因为令牌头部写了 `alg` 就无条件照做。必须由服务端预先限定允许的算法，并确保密钥与算法匹配；拒绝意料之外的 `none`、错误算法或验证失败的令牌。解析出合法 JSON 只说明“读懂了数据”，不说明“信任了数据”。

## 加密保护的是秘密，不是身份声明

对称加密的特点是加密和解密使用同一把密钥，适合大量数据。现代应用通常选择经过认证的加密模式，例如 AES-GCM：在保护明文机密性的同时，验证密文未被篡改。每次加密所需的随机数或 nonce 必须按算法要求正确生成；同一密钥下错误地复用 nonce 会造成严重风险。

非对称密码体系使用公钥与私钥，但“公钥加密、私钥解密”和“私钥签名、公钥验签”是两个不同目的的操作，不能把签名理解为“用私钥加密”。TLS 会利用密码学握手建立受保护的连接，随后保护浏览器和服务器之间的传输；它解决的是链路问题，不会自动替代密码存储、令牌验证或数据库权限控制。

普通 JWS 载荷可被读取，因此需要对令牌里的声明保密时，应重新评估是否真要把这些信息放在令牌中。能只放不敏感标识、需要时回服务端查询，就不要为“把一切塞进 JWT”承担额外复杂度。

## 过期时间不是登出按钮

签名正确的令牌也可能已经过期，或者虽然尚未过期却已不该继续使用。服务端至少应按应用约定校验 `exp` 等时间字段、`iss`、`aud` 和签名。`exp` 控制的是令牌最晚可接受时间，不代表用户点击“退出”后所有已签发的令牌会自动失效。

如果业务要求退出后立即失效，可采用短期访问令牌配合可撤销的刷新令牌、服务端会话、撤销列表或令牌版本号等方案；这些方案在状态管理和请求开销上各有取舍。令牌放在浏览器的何处也影响风险：脚本可读取的存储更需防 XSS；Cookie 应结合 `HttpOnly`、`Secure`、恰当的 `SameSite` 设置，并评估 CSRF。无论存放方式如何，HTTPS 都是基础。

## 一个实用的判断顺序

遇到“这里要不要加密”时，可以依次问五个问题：

1. **只是变换表示吗？** 用编码，但不要把编码当安全保护。
2. **只需验证输入是否与原来一致吗？** 密码用专门的慢速密码哈希；普通内容完整性校验可用哈希。
3. **需要证明消息未被改、确由可信一方生成吗？** 考虑 HMAC 或数字签名，并规划密钥保管和轮换。
4. **内容不该被旁观者读到吗？** 传输使用 HTTPS；静态或业务数据按威胁模型采用合适的认证加密。
5. **凭证泄漏、过期和撤销怎么办？** 定义有效期、存储方式、权限检查、轮换及退出策略。

回到 JWT 登录：Base64url 让令牌可传输，签名让声明难以伪造，密码哈希保护数据库中的密码，TLS 保护传输，授权规则决定用户能做什么，令牌生命周期决定信任能持续多久。把这些职责分清，比记住更多算法名字更重要。
